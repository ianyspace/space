## MySQL 架构与存储引擎

### 基础概念

MySQL 是一个关系型数据库管理系统，采用分层架构设计，将连接管理、SQL 处理和数据存储解耦，使得存储引擎可以独立替换。

### 原理深入

#### MySQL 整体架构

<arch-figure caption="MySQL 的三层架构，以及一条 SELECT 依次走过的七个步骤"></arch-figure>

#### 一条 SELECT 的执行流程

1. **客户端** 发送 SQL
2. **连接器** 验证权限、建立连接
3. **解析器** 词法分析（识别关键字、表名、列名）→ 语法分析（构建语法树 AST）
4. **预处理器** 检查表和列是否存在、展开 `SELECT *`、权限验证
5. **优化器** 选择使用哪个索引、多表关联时决定连接顺序、生成执行计划
6. **执行器** 校验权限 → 调用存储引擎接口逐行获取数据 → 返回结果集
7. **存储引擎** 从磁盘/缓存读取数据页，返回给执行器

#### InnoDB vs MyISAM

| 对比项 | InnoDB | MyISAM |
|--------|--------|--------|
| 事务 | 支持（ACID） | 不支持 |
| 锁粒度 | 行级锁（基于索引） | 表级锁 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | 支持（redo log） | 不支持，可能丢数据 |
| 聚簇索引 | 支持（数据与主键索引绑定） | 不支持（非聚簇） |
| MVCC | 支持 | 不支持 |
| 全文索引 | MySQL 5.6+ 支持 | 支持 |
| COUNT(*) | 需要扫描（MVCC 原因） | 内部维护计数器，直接返回 |
| 默认引擎 | MySQL 5.5+ 默认 | 早期默认 |
| 适用场景 | 高并发、需要事务的 OLTP | 读多写少、不需要事务的场景 |

**为什么默认选 InnoDB**：
1. 支持事务，保证 ACID，数据安全
2. 行级锁，并发性能好
3. redo log 实现 crash-safe，断电不丢数据
4. MVCC 实现读写不冲突，高并发下吞吐量高
5. 聚簇索引让主键查询极快

### 问答实战（精讲及回答）

#### ⭐⭐ 说一下 MySQL 的架构

**提问意图**：考察对 MySQL 整体理解，能不能从全局视角描述清楚。

**推荐回答**：

> MySQL 是分层架构，从上到下分为三层：连接层、服务层和存储引擎层。
>
> 连接层负责处理客户端连接，包括连接池和认证鉴权。服务层是核心，包含解析器做词法分析和语法分析生成语法树，预处理器检查表和列是否存在，优化器选择索引和执行计划，执行器调用存储引擎接口执行查询。存储引擎层是可插拔的，不同的引擎负责数据的实际存储和读取，最常用的是 InnoDB。
>
> 一条 SELECT 的执行路径是：连接器验证 → 解析器分析 → 预处理器检查 → 优化器生成执行计划 → 执行器调用存储引擎取数据 → 返回结果。

**追问准备**：
- "查询缓存是什么？" → MySQL 5.5/5.6 时代有 Query Cache，以 SQL 文本为 key 缓存结果。但问题是任何表的写操作都会清空该表的所有缓存，命中率很低，MySQL 8.0 已经移除了。

---

#### ⭐⭐ InnoDB 和 MyISAM 的区别？为什么选 InnoDB？

**提问意图**：基础但重要，看候选人对存储引擎有没有概念。

**推荐回答**：

> 两者最核心的区别在四个方面。第一，InnoDB 支持事务和 ACID，MyISAM 不支持，写入中断可能导致数据损坏。第二，InnoDB 支持行级锁（基于索引），MyISAM 只有表级锁，并发场景下 InnoDB 性能好得多。第三，InnoDB 支持外键约束，MyISAM 不支持。第四，InnoDB 通过 redo log 实现崩溃恢复，断电重启后数据不会丢，MyISAM 没有这个机制。
>
> MyISAM 的优势是 COUNT(*) 快（内部维护了计数器），全文索引在早期版本也更好。但这些优势在 MySQL 5.6+ 之后被 InnoDB 逐步追平了。
>
> 选 InnoDB 的根本原因是事务安全和并发性能。实际业务中几乎没有不需要事务的场景，而且 InnoDB 的 MVCC 让读写互不阻塞，高并发下吞吐量远超 MyISAM。

### 问答速查表

| 考点 | 一句话答案 |
|------|-----------|
| 三层架构 | 连接层（连接池+认证）→ 服务层（解析+优化+执行）→ 存储引擎层 |
| SELECT 流程 | 连接器 → 解析器 → 预处理器 → 优化器 → 执行器 → 存储引擎 |
| 优化器职责 | 选索引、决定连接顺序、生成执行计划 |
| InnoDB 优势 | 事务/行锁/外键/crash-safe/MVCC/聚簇索引 |
| MyISAM 特点 | 表锁/无事务/无外键/COUNT(*) 快/不支持崩溃恢复 |
| 默认引擎 | MySQL 5.5+ 默认 InnoDB |
| 查询缓存 | SQL 文本为 key，写操作清空整表缓存，8.0 已移除 |

## 索引（核心重点）

### 基础概念

索引是数据库为了加速数据检索而维护的一种有序数据结构，类似于书的目录。没有索引的查询需要全表扫描，有索引可以将时间复杂度从 O(n) 降到 O(log n)。

MySQL 的索引是在**存储引擎层**实现的，不同引擎的索引实现不同。

### 原理深入

#### B+ 树结构与原理

InnoDB 的索引基于 **B+ 树**实现：

<btree-figure caption="B+ 树：非叶子只存键，叶子存数据，并且按顺序串成双向链表"></btree-figure>

**B+ 树特点**：
- 非叶子节点只存键，不存数据 → 一页能放更多键 → 树更矮 → 磁盘 IO 更少
- 所有数据都在叶子节点 → 查询性能稳定，每次都走到叶子
- 叶子节点通过双向链表连接 → 范围查询高效（顺着链表扫）

**为什么不用其他数据结构？**

| 结构 | 问题 |
|------|------|
| Hash | 等值查询 O(1) 很快，但不支持范围查询、排序 |
| B 树 | 非叶子节点也存数据，一页能放的键少，树更高，IO 更多 |
| 红黑树 | 二叉树，数据量大时树很高，IO 次数多 |
| 跳表 | 不是磁盘友好型结构，Redis 用但 MySQL 不用 |

**树的高度与数据量**（假设每页 16KB，主键 bigint 8字节，指针 6字节）：
- 非叶子节点每页约放 1170 个键
- 叶子节点每页约放 16 条完整行（假设每行 1KB）
- 2 层 B+ 树：1170 × 16 ≈ **1.8 万条**
- 3 层 B+ 树：1170 × 1170 × 16 ≈ **2200 万条**
- 通常 3 层 B+ 树就能支撑千万级数据，查询只需 2~3 次磁盘 IO

#### 聚簇索引 vs 非聚簇索引

**聚簇索引（Clustered Index）**：
- 叶子节点存储**整行数据**
- InnoDB 中就是主键索引
- 一张表只能有一个聚簇索引
- 数据和索引绑定在一起，所以叫"聚簇"

**非聚簇索引（Secondary Index）**：
- 叶子节点存储的是**主键值**（不是行数据）
- 也叫二级索引

<index-figure caption="聚簇索引的叶子是整行，二级索引的叶子是主键 —— 中间那一步就是回表"></index-figure>

**回表查询**：通过二级索引查到主键值后，需要再到聚簇索引中查完整行数据，这个过程叫回表，多一次 B+ 树查询。

```sql
-- 假设 name 上有二级索引
-- 回表查询：先在 name 索引找到 id=5，再在聚簇索引查 id=5 的完整行
SELECT * FROM user WHERE name = '张三';

-- 覆盖索引：查询的列都在二级索引中，不需要回表
SELECT name FROM user WHERE name = '张三';
```

#### 主键索引 / 唯一索引 / 普通索引 / 联合索引

| 索引类型 | 特点 | 示例 |
|---------|------|------|
| 主键索引 | 唯一 + 非空，聚簇索引，一张表只有一个 | PRIMARY KEY (id) |
| 唯一索引 | 值唯一，允许 NULL，可以有多个 | UNIQUE KEY (email) |
| 普通索引 | 无约束，可以有重复值 | KEY (name) |
| 联合索引 | 多个列组合，遵循最左前缀 | KEY (a, b, c) |

#### 最左前缀匹配原则（高频考点）

联合索引 `(a, b, c)` 在 B+ 树中的排序规则：
- 先按 a 排序
- a 相同时按 b 排序
- a 和 b 都相同时按 c 排序

所以联合索引只有从最左列开始匹配才能生效：

<leftmost-lab caption="联合索引 (a, b, c)：点一条 WHERE，看索引用上了哪几列"></leftmost-lab>

**范围查询的影响**：
```sql
-- 联合索引 (a, b, c)
WHERE a = 1 AND b > 5 AND c = 3
-- 用到 a, b，c 用不上（范围查询右侧的列无法利用索引排序/过滤）
-- 但在 MySQL 8.0 中，c 可能通过索引下推（ICP）在引擎层过滤
```

#### 覆盖索引

当查询的列全部包含在某个二级索引中时，不需要回表，称为覆盖索引。

```sql
-- 联合索引 (name, age)
SELECT name, age FROM user WHERE name = '张三';
-- name 和 age 都在索引中，叶子节点直接拿到，不用回表
-- EXPLAIN 中 Extra 列显示 Using index
```

**覆盖索引是性能优化的重要手段**：避免了回表的随机 IO，查询速度可以提升数倍。

#### 索引下推（Index Condition Pushdown, ICP）

MySQL 5.6 引入的优化。对于二级索引中无法直接用于过滤的列，将过滤条件下推到存储引擎层执行，减少回表次数。

```sql
-- 联合索引 (a, b)
SELECT * FROM t WHERE a = 1 AND b LIKE 'abc%';

-- 没有 ICP：先用 a=1 从索引查出所有匹配行 → 逐行回表 → Server 层过滤 b
-- 有 ICP：在引擎层，用索引中的 b 值先过滤 LIKE 'abc%'，不匹配的跳过不回表
-- EXPLAIN 中 Extra 显示 Using index condition
```

#### 索引失效的常见场景

```sql
-- 1. 对索引列做函数/表达式运算
WHERE YEAR(create_time) = 2026          ❌ 失效
WHERE create_time >= '2026-01-01'       ✅ 正确

-- 2. 隐式类型转换
WHERE phone = 13800138000              ❌ phone 是 varchar，传了数字，触发转换
WHERE phone = '13800138000'            ✅ 正确

-- 3. LIKE 左模糊
WHERE name LIKE '%张'                   ❌ 全表扫描
WHERE name LIKE '张%'                   ✅ 走索引

-- 4. OR 条件中有一个列没有索引
WHERE a = 1 OR b = 2                   ❌ 如果 b 没索引，整个条件不走索引

-- 5. NOT IN / NOT EXISTS（部分场景）
-- 优化器可能判断全表扫描比走索引更快

-- 6. 联合索引不满足最左前缀
WHERE b = 2 AND c = 3                  ❌ 索引 (a,b,c) 缺最左列

-- 7. IS NULL / IS NOT NULL
-- 取决于数据分布，优化器可能选择全表扫描

-- 8. 优化器判断全表扫描更快（数据量小 / 区分度低）
-- 即使有索引，优化器评估后认为全表扫描成本更低就不走索引
```

### 问答实战（精讲及回答）

#### ⭐⭐⭐ 为什么 MySQL 用 B+ 树做索引？

**提问意图**：索引章节最高频的题目，考察数据结构选型能力。

**推荐回答**：

> B+ 树相比其他数据结构，在数据库磁盘 IO 场景下是最优选择。
>
> 先说为什么不用 Hash。Hash 的等值查询是 O(1)，确实很快，但它完全不支持范围查询、排序和模糊查询。数据库的查询场景远不止等值匹配，所以 Hash 不适合作为通用索引结构。
>
> 再说为什么不用 B 树。B 树的非叶子节点也存储数据，而 B+ 树非叶子节点只存键值不存数据。这意味着 B+ 树每个非叶子节点能放下更多的键，树就更矮。假设一个 16KB 的页，B+ 树能放约 1170 个键，三层 B+ 树就能容纳 2000 多万条数据，只需要三次磁盘 IO。B 树因为非叶子也存数据，每个节点能放的键少，树更高，IO 更多。
>
> 另外 B+ 树的叶子节点通过双向链表连接，做范围查询时只要定位到起始叶子节点然后顺着链表扫就行，非常高效。B 树的叶子之间没有链表，范围查询需要中序遍历整棵树。
>
> 最后红黑树是二叉树，数据量大时树很高，IO 次数多。B+ 树是多叉的，天然矮胖，适合磁盘 IO 场景。

---

#### ⭐⭐⭐ 什么是聚簇索引和非聚簇索引？回表是什么？

**提问意图**：考察对 InnoDB 索引结构的理解深度。

**推荐回答**：

> InnoDB 中有两种索引：聚簇索引和非聚簇索引（也叫二级索引）。
>
> 聚簇索引就是主键索引，它的 B+ 树叶子节点存储的是整行数据。InnoDB 要求每张表必须有且仅有一个聚簇索引，如果没有显式定义主键，InnoDB 会找一个唯一非空索引代替，都没有就自动生成一个隐藏的 rowid 做聚簇索引。因为数据就存在聚簇索引的叶子节点上，所以主键查询非常快，一次 B+ 树搜索就能拿到完整行。
>
> 非聚簇索引就是二级索引，叶子节点存的是主键值而不是行数据。当通过二级索引查询时，先在二级索引的 B+ 树中找到主键值，然后拿着主键值再到聚簇索引的 B+ 树中查完整行数据，这个二次查找的过程就叫回表。
>
> 回表意味着多一次 B+ 树遍历，如果回表量大性能会明显下降。优化手段是覆盖索引——让查询需要的列都在二级索引中，不需要回表。

**追问准备**：
- "为什么 InnoDB 建议用自增主键？" → 聚簇索引按主键排序，自增主键让新数据总是插入到 B+ 树的末尾，不会导致页分裂。如果用 UUID 或字符串做主键，插入位置随机，频繁触发页分裂和数据搬移，写入性能很差。
- "没有主键 InnoDB 怎么处理？" → 先找第一个唯一非空索引作为聚簇索引；没有就自动生成一个 6 字节的隐藏 rowid。

---

#### ⭐⭐ 说一下最左前缀匹配原则

**提问意图**：联合索引的核心规则，问答高频。

**推荐回答**：

> 最左前缀匹配原则是针对联合索引来说的。比如建了联合索引 (a, b, c)，B+ 树中的排序规则是先按 a 排序，a 相同时按 b 排序，a 和 b 都相同时按 c 排序。
>
> 这意味着查询条件必须从联合索引的最左列开始连续匹配才能用到索引。WHERE a=1 AND b=2 AND c=3 完整匹配三列。WHERE a=1 AND b=2 匹配前两列。但 WHERE b=2 AND c=3 缺少最左列 a，就用不上这个索引，因为 b 在全局上不是有序的，只有在 a 相同的前提下 b 才有序。
>
> 还有一个重要的规则：遇到范围查询就断了。比如 WHERE a=1 AND b>5 AND c=3，a 和 b 可以用索引，但 b 是范围查询，c 就用不上了。不过在 MySQL 8.0 中引入了索引跳跃扫描，某些场景下即使缺最左列也能部分利用索引。
>
> 设计联合索引时应该把区分度高的列放前面，等值查询的列放前面，范围查询的列放后面。

---

#### ⭐⭐ 索引失效有哪些场景？

**提问意图**：实战经验考察，看有没有真正调过 SQL。

**推荐回答**：

> 常见的索引失效场景有这么几种。
>
> 第一，对索引列做函数运算或表达式计算，比如 WHERE YEAR(create_time) = 2026，MySQL 无法直接在索引树上做函数匹配，只能全表扫描。应该改成范围条件 WHERE create_time >= '2026-01-01' AND create_time < '2027-01-01'。
>
> 第二，隐式类型转换。字段是 varchar 但传了数字，MySQL 会对字段做隐式转换，导致索引失效。这类问题很隐蔽，排查时需要仔细看字段类型和参数类型是否匹配。
>
> 第三，LIKE 左模糊查询，LIKE '%张' 无法走索引，因为索引是从左到右排序的，左边不确定就没法二分查找。
>
> 第四，联合索引不满足最左前缀，缺最左列就用不上。
>
> 第五，OR 条件中有非索引列，会导致整个条件不走索引。
>
> 第六，优化器判断全表扫描更快。比如表很小、或者查询条件区分度太低（如性别字段只有男和女），优化器评估走索引反而比全表扫描慢，就会选择全表扫描。

### 问答速查表

| 考点 | 一句话答案 |
|------|-----------|
| B+ 树优势 | 非叶子不存数据→更矮→更少 IO；叶子双向链表→范围查询高效 |
| 聚簇索引 | 主键索引，叶子存整行数据，一张表只有一个 |
| 非聚簇索引 | 二级索引，叶子存主键值，需要回表 |
| 回表 | 二级索引查到主键后再查聚簇索引拿完整行，多一次 B+ 树搜索 |
| 覆盖索引 | 查询列全在二级索引中，不用回表，EXPLAIN 显示 Using index |
| 最左前缀 | 联合索引 (a,b,c)，必须从 a 开始连续匹配，范围查询右侧断裂 |
| 索引失效 | 函数运算/隐式转换/LIKE 左模糊/缺最左列/OR 非索引列/优化器判断全表更快 |
| 索引下推 ICP | 二级索引中非过滤列的条件下推到引擎层，减少回表 |
| 自增主键 | 顺序插入避免页分裂，UUID 随机插入导致频繁分裂 |
| 树高度 | 三层 B+ 树约支撑 2000 万条数据，2~3 次 IO |

## 事务

### 基础概念

事务是数据库操作的逻辑单元，一组 SQL 要么全部成功，要么全部回滚。MySQL 中只有 InnoDB 引擎支持事务。

### 原理深入

#### ACID 四大特性

| 特性 | 含义 | 实现机制 |
|------|------|---------|
| **A**tomicity（原子性） | 事务中的操作要么全做，要么全不做 | undo log（回滚日志） |
| **C**onsistency（一致性） | 事务前后数据库从一个一致状态到另一个一致状态 | A + I + D 共同保证 |
| **I**solation（隔离性） | 并发事务之间互不干扰 | 锁 + MVCC |
| **D**urability（持久性） | 事务提交后数据永久保存，即使系统崩溃 | redo log（重做日志） |

> 一致性是最终目标，原子性、隔离性、持久性都是保证一致性的手段。

#### 事务隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能 |
|---------|------|-----------|------|------|
| 读未提交（Read Uncommitted） | ❌ 会 | ❌ 会 | ❌ 会 | 最高 |
| 读已提交（Read Committed） | ✅ 不会 | ❌ 会 | ❌ 会 | 高 |
| 可重复读（Repeatable Read） | ✅ 不会 | ✅ 不会 | ⚠️ 部分解决 | 中 |
| 串行化（Serializable） | ✅ 不会 | ✅ 不会 | ✅ 不会 | 最低 |

**三个并发问题**：

<isolation-figure caption="脏读、不可重复读、幻读：同样是读到了不该读的，差别在箭头插在哪一步"></isolation-figure>

#### MySQL 默认隔离级别：可重复读（RR）

MySQL 选择 RR 作为默认级别的原因：
1. RC 级别下，同一事务内多次读取结果可能不同，容易引发业务逻辑错误
2. RR 通过 MVCC 的 Read View 机制，保证同一事务内读到的数据始终一致
3. RR 级别下 InnoDB 通过间隙锁（Gap Lock）和 Next-Key Lock 在很大程度上解决了幻读问题

**RR vs RC 的核心区别**：
- RC：每次 SELECT 都生成新的 Read View（每次读都是最新已提交的）
- RR：只在事务第一次 SELECT 时生成 Read View，后续复用（整个事务期间读到的数据一致）

### 问答实战（精讲及回答）

#### ⭐⭐ 事务的 ACID 分别是什么？怎么实现的？

**提问意图**：事务基础题，关键看能不能说出实现机制。

**推荐回答**：

> ACID 是原子性、一致性、隔离性、持久性。
>
> 原子性指事务中的操作要么全部成功，要么全部回滚。通过 undo log 实现，事务执行时会记录 undo log，如果回滚就用 undo log 把数据还原。
>
> 持久性指事务提交后数据永久保存，即使系统崩溃也不会丢失。通过 redo log 实现，采用 WAL（Write-Ahead Logging）策略，修改数据时先写 redo log 到磁盘，即使 MySQL 进程崩溃，重启后也能通过 redo log 恢复已提交的数据。
>
> 隔离性指并发事务之间互不干扰。通过锁机制和 MVCC 实现。锁防止写冲突，MVCC 让读写操作不互相阻塞。
>
> 一致性是最终目标，指事务前后数据库处于一致状态。它不是单独实现的，而是原子性、隔离性和持久性共同保证的结果。

#### ⭐⭐⭐ MySQL 的四种隔离级别？区别是什么？

**提问意图**：高频必考，考察对并发问题的精确理解。

**推荐回答**：

> MySQL 支持四种隔离级别，从低到高分别是：读未提交、读已提交、可重复读、串行化。
>
> 读未提交是最低级别，一个事务能读到其他事务还没提交的数据，会脏读。基本没人用。
>
> 读已提交解决了脏读，只能读到已提交的数据。但同一个事务中两次读同一行数据，如果中间有其他事务提交了这个行的修改，两次读的结果不一样，这叫不可重复读。Oracle 默认就是这个级别。
>
> 可重复读解决了不可重复读，保证同一事务中多次读同一行数据结果一致。MySQL 默认就是这个级别。实现方式是 MVCC，事务第一次 SELECT 时生成一个 Read View 快照，后续所有读都基于这个快照。但幻读问题只部分解决——通过间隙锁防止了新增行的幻读，但在某些场景下仍可能出现。
>
> 串行化是最高级别，所有事务串行执行，完全解决了脏读、不可重复读和幻读，但并发性能最差。

**追问准备**：
- "RR 和 RC 在 MVCC 层面的区别？" → RC 每次 SELECT 都重新生成 Read View，所以能读到其他事务最新提交的数据。RR 只在第一次 SELECT 时生成 Read View 并复用，所以整个事务期间读到的数据一致。
- "RR 能完全解决幻读吗？" → 大部分场景可以。快照读通过 MVCC 的 Read View 解决，当前读（SELECT ... FOR UPDATE）通过间隙锁和 Next-Key Lock 解决。但在某些特殊场景下（先快照读再当前读），仍可能出现幻读。

#### ⭐ 脏读、不可重复读、幻读的区别？

**提问意图**：概念辨析，要求能用自己的话说清楚。

**推荐回答**：

> 这三个都是并发事务导致的数据不一致问题，区别在于"读到了什么不该读的东西"。
>
> 脏读是读到了其他事务还没提交的数据。那个事务可能回滚，所以读到的是"脏"数据。比如 A 读到 B 改的余额 200，但 B 回滚了，余额其实还是 100。
>
> 不可重复读是同一事务中两次读同一行数据，结果不同。因为中间有其他事务修改了这一行并提交了。重点在于"修改"——同一行数据被改了。
>
> 幻读是同一事务中两次范围查询，结果行数不同。因为中间有其他事务插入了新行或删除了行。重点在于"新增/减少"——多了或少了几行。
>
> 简单记：脏读读到了未提交的修改，不可重复读读到了已提交的修改，幻读读到了已提交的插入。

| 考点 | 一句话答案 |
|------|-----------|
| ACID | 原子性(undo log)/一致性(ACD共同)/隔离性(锁+MVCC)/持久性(redo log) |
| 读未提交 | 能读未提交数据，会脏读/不可重复读/幻读 |
| 读已提交 | 只读已提交，解决脏读，会不可重复读/幻读（Oracle 默认） |
| 可重复读 | 同一事务读取一致，解决脏读+不可重复读，部分解决幻读（MySQL 默认） |
| 串行化 | 完全串行执行，解决所有问题，性能最差 |
| 脏读 | 读到未提交的修改 |
| 不可重复读 | 同一事务两次读同一行不同（被修改） |
| 幻读 | 同一事务两次范围查询行数不同（被插入/删除） |
| RR vs RC | RR 第一次 SELECT 生成 Read View 并复用；RC 每次 SELECT 重新生成 |

## MVCC（多版本并发控制）

### 基础概念

MVCC（Multi-Version Concurrency Control）是 InnoDB 实现高并发的核心机制。它让读操作不需要加锁就能读到一致性数据，读写操作互不阻塞，大幅提升并发性能。

核心思想：**读不加锁，读写不冲突**。通过保存数据的历史版本来实现。

### 原理深入

#### 隐藏字段

InnoDB 为每行数据自动添加三个隐藏字段：

| 字段 | 大小 | 说明 |
|------|------|------|
| DB_TRX_ID | 6 字节 | 最近一次修改该行的事务 ID |
| DB_ROLL_PTR | 7 字节 | 回滚指针，指向 undo log 中的旧版本 |
| DB_ROW_ID | 6 字节 | 隐藏自增 rowid（没有主键时使用） |

#### Undo Log 版本链

每次 UPDATE 操作会把旧版本写入 undo log，并通过 DB_ROLL_PTR 形成版本链：

<mvcc-figure caption="一条版本链加一张 Read View：从最新版本往回走，第一个可见的版本就是答案"></mvcc-figure>

版本链从新到旧排列，每个节点记录了对应的事务 ID。MVCC 的 Read View 就是在这条链上找到"对当前事务可见"的版本。

#### Read View（读视图）

Read View 在事务进行快照读时生成，包含四个核心字段：

| 字段 | 说明 |
|------|------|
| m_ids | 生成 Read View 时，所有**活跃（未提交）** 事务的 ID 列表 |
| min_trx_id | m_ids 中的最小值 |
| max_trx_id | 生成 Read View 时，系统即将分配的下一个事务 ID（最大 trx_id + 1） |
| creator_trx_id | 创建这个 Read View 的事务 ID |

#### 可见性判断规则

对于版本链中某个版本的 trx_id：

1. `trx_id == creator_trx_id` → 自己改的，可见 ✅
2. `trx_id < min_trx_id` → Read View 创建之前就提交了，可见 ✅
3. `trx_id >= max_trx_id` → Read View 创建之后才开始的事务，不可见 ❌
4. `min_trx_id <= trx_id < max_trx_id` → 看 `trx_id` 在不在 `m_ids` 里：
   - 在列表里 → 生成 Read View 时它还没提交，不可见 ❌
   - 不在列表里 → 生成 Read View 时它已经提交了，可见 ✅

如果当前版本不可见，就顺着 DB_ROLL_PTR 找更早的版本，直到找到可见的版本或版本链结束。

#### MVCC 如何解决不可重复读

**RR 级别下**：
```text
事务 A                                事务 B
BEGIN;
SELECT balance → 100
（第一次 SELECT，生成 Read View）
                                       BEGIN;
                                       UPDATE balance = 200;
                                       COMMIT;
SELECT balance → 100  ✅（复用第一次的 Read View，看不到 B 的修改）
```

**RC 级别下**：
```text
事务 A                                事务 B
BEGIN;
SELECT balance → 100
                                       BEGIN;
                                       UPDATE balance = 200;
                                       COMMIT;
SELECT balance → 200  ❌（每次 SELECT 重新生成 Read View，看到了 B 的提交）
```

#### 快照读 vs 当前读

| 类型 | SQL | 说明 |
|------|-----|------|
| 快照读 | SELECT ... WHERE ... | 不加锁，基于 MVCC Read View 读历史版本 |
| 当前读 | SELECT ... FOR UPDATE / LOCK IN SHARE MODE | 加锁，读最新已提交数据 |
| 当前读 | INSERT / UPDATE / DELETE | 加锁，操作最新数据 |

**MVCC 只对快照读生效**。当前读需要加锁保证一致性。

### 问答实战（精讲及回答）

#### ⭐⭐⭐ 说一下 MVCC 的原理

**提问意图**：中级问答的区分度考点，能讲清楚说明对 InnoDB 理解深入。

**推荐回答**：

> MVCC 的全称是多版本并发控制，核心目标是让读操作不加锁就能读到一致性数据，读写互不阻塞。
>
> 它依赖三个机制协同工作：隐藏字段、undo log 版本链和 Read View。
>
> 首先，InnoDB 给每行数据加了两个隐藏字段：DB_TRX_ID 记录最近修改这个行的事务 ID，DB_ROLL_PTR 是指向 undo log 中旧版本的回滚指针。每次 UPDATE 都会把旧版本保存到 undo log 中，通过 DB_ROLL_PTR 串成一条从新到旧的版本链。
>
> 然后是 Read View，也叫读视图。事务做快照读时会生成一个 Read View，记录了生成时刻有哪些事务还没提交（m_ids 列表）、最小和最大事务 ID 等信息。
>
> 查询时从版本链的最新版本开始，用 Read View 的规则判断这个版本对当前事务是否可见：如果版本的 trx_id 小于最小活跃事务 ID，说明在 Read View 创建前就提交了，可见；如果大于等于最大事务 ID，说明在 Read View 创建后才开始，不可见；如果在范围内就看是不是在未提交事务列表中。不可见就顺着版本链找更早的版本，直到找到可见的。
>
> RR 和 RC 的区别就在于 Read View 的生成时机：RR 只在第一次 SELECT 时生成并复用，所以整个事务期间读到的数据一致；RC 每次 SELECT 都重新生成，所以能看到其他事务的最新提交。

**追问准备**：
- "快照读和当前读的区别？" → 快照读就是普通的 SELECT，不加锁，走 MVCC 读历史版本。当前读包括 SELECT FOR UPDATE、SELECT LOCK IN SHARE MODE、INSERT、UPDATE、DELETE，都加锁读最新数据。MVCC 只对快照读生效。
- "MVCC 能解决幻读吗？" → 快照读通过 MVCC 解决，因为 Read View 固定了，看不到其他事务新插入的行。但当前读（比如 SELECT FOR UPDATE 后再 INSERT）需要依赖间隙锁和 Next-Key Lock 来防止。

#### ⭐⭐ RR 级别下 MVCC 怎么解决不可重复读？

**提问意图**：MVCC 和事务隔离的关系，考察串联能力。

**推荐回答**：

> 在 RR 级别下，事务第一次执行快照读时会生成一个 Read View，之后这个事务中所有的快照读都复用这个 Read View，不会重新生成。
>
> 这意味着这个事务读到的数据永远是"第一次读那个时刻"的快照。即使其他事务在这期间修改了数据并提交了，当前事务也看不到，因为 Read View 中记录的活跃事务列表没变，那些后来提交的事务 ID 对于当前 Read View 来说属于"创建之后才开始的"，会被判断为不可见。
>
> 对比 RC 级别，RC 每次 SELECT 都重新生成 Read View，所以能读到最新提交的数据，同一事务中两次读结果可能不同，就产生了不可重复读。
>
> 所以 RR 解决不可重复读的核心就一句话：Read View 只生成一次，整个事务期间看到的数据一致。

### 问答速查表

| 考点 | 一句话答案 |
|------|-----------|
| MVCC 目的 | 读不加锁，读写不冲突，提升并发性能 |
| 隐藏字段 | DB_TRX_ID(修改事务ID) / DB_ROLL_PTR(指向旧版本) / DB_ROW_ID |
| 版本链 | undo log 通过 DB_ROLL_PTR 串成链，从新到旧排列 |
| Read View | 记录生成时刻的活跃事务列表，用于判断版本可见性 |
| 可见性规则 | trx_id < min → 可见；>= max → 不可见；在范围内看是否在 m_ids |
| RR 解决不可重复读 | 第一次 SELECT 生成 Read View 并复用，整个事务数据一致 |
| RC 有不可重复读 | 每次 SELECT 重新生成 Read View，能看到新提交 |
| 快照读 | 普通 SELECT，不加锁，走 MVCC |
| 当前读 | SELECT FOR UPDATE / INSERT / UPDATE / DELETE，加锁读最新 |

## 锁机制

### 基础概念

InnoDB 支持多种粒度的锁，从粗到细分为：全局锁、表级锁、行级锁。锁的目的是保证并发访问时的数据一致性和完整性。

### 原理深入

#### 全局锁

```sql
-- 对整个数据库实例加锁，只读
FLUSH TABLES WITH READ LOCK;

-- 使用场景：全库逻辑备份
-- 备份完成后解锁
UNLOCK TABLES;
```

备份时为什么不直接用 `set global readonly = true`？因为 readonly 在从库上用于主从同步，改了会影响复制。FTWRL 是专门用于备份的全局只读锁。

#### 表级锁

| 锁类型 | 说明 |
|--------|------|
| 表共享读锁（S） | 其他事务可以读但不能写 |
| 表独占写锁（X） | 其他事务不能读也不能写 |
| 意向锁（IS/IX） | 内部锁，无需手动管理（下面详述） |
| 自增锁（AUTO-INC） | INSERT 时获取自增值，语句级释放 |
| 元数据锁（MDL） | DDL 时自动加，防止 DML 和 DDL 并发 |

```sql
-- 手动加表锁（很少用）
LOCK TABLES t1 READ, t2 WRITE;
UNLOCK TABLES;
```

**元数据锁（MDL）的坑**：MDL 会造成「排队头阻塞」，一张表的 DDL 能把整张表的读写全堵死。

1. 长事务持有一张表的 MDL 共享锁（普通的 `SELECT` 也会拿）。
2. 这时有人执行 DDL，需要 MDL 排他锁 —— 被长事务挡住，开始等。
3. **DDL 在等的时候，后面所有要拿这张表 MDL 共享锁的 DML 也会排在 DDL 后面**，整张表的读写一起堵住。
4. 连接池很快被占满，业务全线超时。

解决：先 `kill` 掉那个长事务，DDL 才能拿到锁，后面的 DML 跟着放行。

#### InnoDB 行锁（核心重点）

InnoDB 的行锁是**加在索引上**的，不是加在行上。如果 SQL 没有走索引，行锁会退化为表锁。

**1. 记录锁（Record Lock）**

```sql
-- 锁定索引上的单条记录
SELECT * FROM user WHERE id = 5 FOR UPDATE;
-- 锁住 id=5 这一行，其他事务不能修改
```

**2. 间隙锁（Gap Lock）**

```sql
-- 锁住索引中两个值之间的"空隙"，防止其他事务往空隙里插新行，用来解决幻读
-- 假设索引中有 id=3 和 id=7

-- 5 不存在，等值查询没命中 → 加的是间隙锁
SELECT * FROM t WHERE id = 5 FOR UPDATE;
-- 3 和 7 之间的这段范围被锁住，其他事务 INSERT 不了 id=4/5/6
```

**3. 临键锁（Next-Key Lock）**：记录锁 + 间隙锁的组合，**左开右闭**，是 InnoDB 在 RR 级别下的默认行锁算法。锁住 `(3, 7]` 的意思是：id = 7 这一条记录改不了，id = 4/5/6 这些还不存在的值也插不进来。

**4. 插入意向锁（Insert Intention Lock）**：一种特殊的间隙锁，允许多个事务往同一个间隙的不同位置插入。事务 A 持有 `(3, 7)` 的间隙锁时，事务 B 想插 id = 5 得先拿插入意向锁，与间隙锁冲突，于是被阻塞；但两个事务分别插 id = 5 和 id = 6 时，两个插入意向锁之间并不冲突。

#### 行锁加锁规则总结（RR 隔离级别）

1. **原则一**：加锁的基本单位是 Next-Key Lock（左开右闭）。
2. **原则二**：查找过程中访问到的对象，锁不能提前释放。
3. **优化一**：索引上的等值查询，命中唯一索引 → Next-Key Lock 退化为 Record Lock。
4. **优化二**：索引上的等值查询，未命中 → Next-Key Lock 退化为 Gap Lock。
5. **优化三**：索引上的范围查询 → 不优化，正常加 Next-Key Lock。

```sql
-- 示例：id 是唯一索引，现有值 5, 10, 15

-- 等值查询命中唯一索引 → 记录锁（只锁 id=10 这一条）
SELECT * FROM t WHERE id = 10 FOR UPDATE;

-- 等值查询未命中 → 间隙锁（锁住 12 会落进去的那个间隙 (10, 15)）
SELECT * FROM t WHERE id = 12 FOR UPDATE;

-- 范围查询 → Next-Key Lock（(5, 10] 和 (10, 15]：扫描会锁到第一个不满足条件的记录 15 为止）
SELECT * FROM t WHERE id > 5 AND id <= 10 FOR UPDATE;
```

<lock-lab caption="同样几条语句，换成数轴看锁住了哪一段"></lock-lab>

#### 共享锁（S）vs 排他锁（X）

| 锁类型 | 获取方式 | 兼容关系 |
|--------|---------|---------|
| 共享锁（S） | SELECT ... LOCK IN SHARE MODE | S-S 兼容，S-X 不兼容 |
| 排他锁（X） | SELECT ... FOR UPDATE / INSERT / UPDATE / DELETE | X-S 不兼容，X-X 不兼容 |

#### 意向锁（IS / IX）

意向锁是 InnoDB **自动加**的表级锁，不需要手动管理：

- 事务要对某行加 S 锁前，先自动加 IS 锁（意向共享）
- 事务要对某行加 X 锁前，先自动加 IX 锁（意向排他）

**作用**：快速判断表中是否有行锁。如果要对表加表级 X 锁，只需检查有没有 IS/IX 锁，不需要逐行检查。

|      | IS   | IX   | S    | X    |
| ---- | ---- | ---- | ---- | ---- |
| IS   | 兼容 | 兼容 | 兼容 | 不兼容 |
| IX   | 兼容 | 兼容 | 不兼容 | 不兼容 |
| S    | 兼容 | 不兼容 | 兼容 | 不兼容 |
| X    | 不兼容 | 不兼容 | 不兼容 | 不兼容 |

#### 死锁的产生与排查

**死锁条件**：两个或多个事务互相持有对方需要的锁。

```text
事务 A: 锁住行 1 → 等待行 2
事务 B: 锁住行 2 → 等待行 1
```

**InnoDB 死锁检测**：
- 默认开启（`innodb_deadlock_detect = ON`）
- 检测到死锁时，自动回滚持有最少行锁的事务
- 大量并发时死锁检测本身消耗 CPU（O(n²)），可以关闭检测改用超时（`innodb_lock_wait_timeout`）

**排查方法**：
```sql
-- 查看最近一次死锁信息
SHOW ENGINE INNODB STATUS;

-- 查看当前锁等待
SELECT * FROM information_schema.INNODB_LOCKS;
SELECT * FROM information_schema.INNODB_LOCK_WAITS;

-- 查看当前事务
SELECT * FROM information_schema.INNODB_TRX;
```

**避免死锁的实践**：
1. 事务尽量短小，减少持锁时间
2. 按固定顺序访问表和行
3. 合理设计索引，确保走索引加行锁
4. 降低隔离级别到 RC（没有间隙锁，幻读由应用层控制）

### 问答实战（精讲及回答）

#### ⭐⭐⭐ InnoDB 有哪些行锁？说一下加锁规则

**提问意图**：并发和锁是 MySQL 问答中最高频的话题之一。

**推荐回答**：

> InnoDB 的行锁有四种：记录锁、间隙锁、临键锁和插入意向锁。
>
> 记录锁只锁一条索引记录，比如 SELECT WHERE id=5 FOR UPDATE 锁住 id=5 这一行。间隙锁锁的是两个索引值之间的空隙，比如索引中有 3 和 7，间隙锁就锁住 (3, 7) 这个区间，防止其他事务在这个范围内插入新行，用来解决幻读问题。
>
> 临键锁也叫 Next-Key Lock，是记录锁加间隙锁的组合，左开右闭区间。InnoDB 在 RR 隔离级别下默认使用 Next-Key Lock 算法。比如锁定 (3, 7] 这个区间。
>
> 加锁规则有几个关键原则。第一，加锁的基本单位是 Next-Key Lock。第二，等值查询命中唯一索引时，Next-Key Lock 退化为 Record Lock，只锁当前行不锁间隙，这是最常见的优化。第三，等值查询未命中时退化为 Gap Lock。第四，范围查询不优化，正常加 Next-Key Lock。
>
> 还有一个非常重要的点：InnoDB 的行锁是加在索引上的，不是加在行上的。如果查询没有走索引，行锁会退化成表锁，所有行都被锁住，性能极差。

**追问准备**：
- "什么场景下行锁会退化为表锁？" → 当 SQL 没有使用索引时，InnoDB 无法通过索引定位行，就会对所有行加锁，相当于锁了整张表。所以确保 UPDATE/DELETE 语句的 WHERE 条件走索引非常重要。
- "RC 级别有间隙锁吗？" → 没有。间隙锁只在 RR 及以上级别存在。RC 级别不加间隙锁，幻读问题交给应用层处理，并发性能更好。

#### ⭐⭐ MySQL 死锁怎么排查？

**提问意图**：考察实际问题的排查经验。

**推荐回答**：

> 死锁是两个或多个事务互相持有对方需要的锁，都在等对方释放，谁都推进不了。
>
> InnoDB 默认开启了死锁检测，检测到死锁时会自动回滚持有最少行锁的那个事务，让其他事务继续。可以通过 SHOW ENGINE INNODB STATUS 查看最近一次死锁的详细信息，包括涉及的事务、持有的锁、等待的锁和回滚了哪个事务。
>
> 也可以查 information_schema 下的 INNODB_TRX 看当前活跃事务，INNODB_LOCKS 看当前锁情况，INNODB_LOCK_WAITS 看锁等待关系。
>
> 不过高并发场景下，死锁检测本身可能成为性能瓶颈，因为检测算法是 O(n²) 的。这种情况可以关闭死锁检测（innodb_deadlock_detect = OFF），改用锁等待超时（innodb_lock_wait_timeout），让等待超时的事务自动回滚。
>
> 避免死锁的实践：事务尽量短小，按固定顺序访问数据，确保走索引避免锁升级，降低隔离级别到 RC 可以去掉间隙锁。

#### ⭐ 共享锁和排他锁的区别？

**提问意图**：锁的基础概念。

**推荐回答**：

> 共享锁也叫读锁或 S 锁，多个事务可以同时持有同一行的共享锁，互相兼容。用 SELECT LOCK IN SHARE MODE 获取。
>
> 排他锁也叫写锁或 X 锁，一个事务持有排他锁后，其他事务不能对该行加任何锁。用 SELECT FOR UPDATE 获取，INSERT、UPDATE、DELETE 操作也会自动加排他锁。
>
> 兼容关系是：S 锁和 S 锁兼容（多个事务可以同时读），S 和 X、X 和 X 都不兼容（有写就不能有其他操作）。

## 日志系统

### 基础概念

InnoDB 有三种关键日志，各司其职：

| 日志 | 层级 | 作用 | 核心机制 |
|------|------|------|---------|
| redo log | InnoDB 引擎层 | 崩溃恢复，保证持久性 | WAL（预写日志） |
| undo log | InnoDB 引擎层 | 事务回滚 + MVCC 版本链 | 逻辑日志 |
| binlog | MySQL Server 层 | 主从复制、数据归档恢复 | 追加写入 |

### 原理深入

#### redo log（重做日志）

**作用**：记录"在某个数据页上做了什么修改"，用于崩溃恢复。

**WAL（Write-Ahead Logging）**：修改数据时，先写 redo log 到磁盘，再慢慢把脏页刷盘。这样即使 MySQL 进程崩溃，重启后也能通过 redo log 重做已提交事务的修改。

<redo-ring-figure caption="redo log 是一圈固定大小的环，write pos 追着 checkpoint 跑"></redo-ring-figure>

**redo log 文件状态**：
- `exists`：文件存在且有效
- `active`：正在被写入
- `checkpoint`：已刷盘可以覆盖

**redo log buffer → 磁盘的刷盘时机**：
1. MySQL 进程关闭时
2. redo log buffer 空间不足时
3. 后台线程每隔 1 秒刷一次
4. 事务提交时（由 `innodb_flush_log_at_trx_commit` 控制）

`innodb_flush_log_at_trx_commit` 的三个取值：

| 取值 | 刷盘时机 | 安全性 / 性能 |
| ---- | -------- | ------------- |
| 0 | 每秒刷一次 | 性能最好，崩溃最多丢 1 秒数据 |
| 1 | 事务提交时 fsync | 最安全，性能最差（默认） |
| 2 | 事务提交时写 OS page cache，每秒 fsync | 折中 |

#### binlog（归档日志）

**作用**：MySQL Server 层的逻辑日志，记录所有 DDL 和 DML 语句（不含 SELECT），用于主从复制和数据恢复。

**三种格式**：

| 格式 | 说明 | 优缺点 |
|------|------|--------|
| STATEMENT | 记录原始 SQL | 省空间，但 NOW() 等函数主从可能不一致 |
| ROW | 记录每行数据的变化 | 最准确不丢数据，但占用空间大（默认推荐） |
| MIXED | 混合，普通用 STATEMENT，不确定时用 ROW | 折中 |

**binlog vs redo log 的区别**：

| 对比项 | redo log | binlog |
|--------|----------|--------|
| 层级 | InnoDB 引擎层 | MySQL Server 层 |
| 日志类型 | 物理日志（数据页+偏移量+修改内容） | 逻辑日志（SQL 或行变更） |
| 写入方式 | 环形写，空间固定可覆盖 | 追加写，文件写满后新建文件 |
| 用途 | 崩溃恢复（crash-safe） | 主从复制、数据归档恢复 |
| 刷盘时机 | 事务提交时 / 后台每秒 | 事务提交时 |

#### 两阶段提交（redo log + binlog 协作）

当同时开启 redo log 和 binlog 时，MySQL 用两阶段提交保证两者的一致性：

<commit-figure caption="两阶段提交：两个崩溃点，三条恢复判定"></commit-figure>

**为什么需要两阶段提交？**

如果先写 redo log 再写 binlog：redo log 写完了但 binlog 还没写就崩溃了 → 主库恢复了但从库没这条数据 → 主从不一致。

如果先写 binlog 再写 redo log：binlog 写完了但 redo log 没写就崩溃了 → 主库没恢复但从库多了这条数据 → 主从不一致。

两阶段提交确保：要么两者都有，要么两者都没有。

#### undo log（回滚日志）

**作用**：
1. **事务回滚**：记录修改前的旧值，回滚时用旧值还原
2. **MVCC**：版本链的基础，每个旧版本都存在 undo log 中

undo log 分两种：

- **insert undo log**：`INSERT` 产生。事务提交后就能立即删除 —— 它写出来的行别的事务本来就看不见，没有历史版本要留给谁。
- **update undo log**：`UPDATE` / `DELETE` 产生。要等所有可能用到它的 Read View 都结束之后才能删 —— MVCC 的版本链就挂在这些旧版本上。

undo log 是**逻辑日志**：记录的是反向操作（INSERT 的反向是 DELETE，UPDATE 的反向是反向 UPDATE）。

### 问答实战（精讲及回答）

#### ⭐⭐⭐ redo log 和 binlog 的区别？

**提问意图**：日志系统是中级问答的区分度考点。

**推荐回答**：

> redo log 和 binlog 有三个核心区别。
>
> 第一，所属层级不同。redo log 是 InnoDB 引擎层的日志，binlog 是 MySQL Server 层的日志，所有引擎都能写 binlog。
>
> 第二，日志类型不同。redo log 是物理日志，记录的是"在某个数据页的某个偏移量上做了什么修改"。binlog 是逻辑日志，记录的是 SQL 语句或者每行数据的变更内容。
>
> 第三，写入方式不同。redo log 是环形写入，空间固定，写满后从头覆盖，用 write pos 和 checkpoint 来管理。binlog 是追加写入，一个文件写满就新建一个，不会覆盖旧文件。
>
> 用途也不同：redo log 用于崩溃恢复，保证已提交事务的数据不丢，这是 InnoDB 独有的能力，MyISAM 没有 redo log 所以不支持 crash-safe。binlog 用于主从复制和数据归档恢复。

---

#### ⭐⭐⭐ 说一下两阶段提交

**提问意图**：考察对 redo log 和 binlog 协作机制的理解。

**推荐回答**：

> 两阶段提交是 MySQL 为了保证 redo log 和 binlog 数据一致性的机制。
>
> 事务提交时，分三步执行。第一步是 Prepare 阶段，把 redo log 写入磁盘，但标记为 prepare 状态，表示还没最终提交。第二步，把 binlog 写入磁盘。第三步是 Commit 阶段，把 redo log 的状态改为 commit。
>
> 崩溃恢复时的判断逻辑：如果 redo log 状态是 commit，说明三步都完成了，直接提交；如果 redo log 状态是 prepare 且 binlog 完整，说明第二步完成了但第三步没完成，也提交；如果 redo log 是 prepare 且 binlog 不完整，说明第二步没写完就崩了，回滚这个事务。
>
> 为什么不能简化为先写 redo log 再写 binlog？因为如果 redo log 写完 binlog 没写完就崩了，主库恢复了但从库没同步到这条数据，主从不一致。反过来先写 binlog 再写 redo log 也有类似问题。两阶段提交通过 prepare 状态的中间态解决了这个两难问题。

**追问准备**：
- "innodb_flush_log_at_trx_commit 怎么选？" → 默认值 1 最安全，事务提交时直接刷盘；设为 0 性能最好但崩溃最多丢 1 秒数据；设为 2 是折中，写到 OS 缓存但每秒才 fsync。对数据安全性要求高的业务保持默认 1。

---

#### ⭐ WAL 是什么？

**提问意图**：数据库设计的核心思想。

**推荐回答**：

> WAL 全称 Write-Ahead Logging，预写日志。核心思想是：修改数据时，先把修改记录写到日志中（redo log），而不是直接把数据页刷到磁盘。数据页的刷盘由后台线程异步完成。
>
> 这样设计的好处有两个。第一，日志是顺序写入磁盘，比随机写数据页快得多，性能大幅提升。第二，即使 MySQL 进程崩溃，重启后也可以通过 redo log 重做已提交事务的修改，保证数据不丢。
>
> 简单说，WAL 就是用顺序 IO 写日志来代替随机 IO 写数据页，同时保证 crash-safe。

### 问答速查表

| 考点 | 一句话答案 |
|------|-----------|
| redo log | InnoDB 层，物理日志，环形写，崩溃恢复用 |
| binlog | Server 层，逻辑日志，追加写，主从复制和归档 |
| undo log | 逻辑日志，记录旧值，事务回滚 + MVCC 版本链 |
| WAL | 先写日志再刷数据页，顺序 IO 快 + crash-safe |
| 两阶段提交 | redo prepare → binlog → redo commit，保证两者一致 |
| redo log 刷盘 | innodb_flush_log_at_trx_commit：0(每秒)/1(提交时)/2(OS缓存) |
| binlog 格式 | STATEMENT(SQL)/ROW(行变更，推荐)/MIXED(混合) |
| redo vs binlog | 引擎层 vs Server 层、物理 vs 逻辑、环形 vs 追加 |
| crash 恢复 | redo commit→提交；prepare+binlog 完整→提交；否则→回滚 |

## SQL 优化

### 基础概念

SQL 优化是后端开发的日常技能。核心思路是：先看执行计划定位问题，再针对性优化。

### 原理深入

#### EXPLAIN 执行计划详解

```sql
EXPLAIN SELECT * FROM user WHERE name = '张三' AND age > 25;
```

| 字段 | 说明 | 关注重点 |
|------|------|---------|
| id | 查询编号，相同则从上到下执行 | 子查询 id 不同，先大后小 |
| select_type | 查询类型 | SIMPLE/PRIMARY/SUBQUERY/UNION/DERIVED |
| table | 访问的表 | — |
| type | 访问类型 | ⭐ 从好到差：system > const > eq_ref > ref > range > index > ALL |
| possible_keys | 可能用到的索引 | — |
| key | 实际使用的索引 | NULL 表示没走索引 |
| key_len | 索引使用的字节数 | 可判断联合索引用了几列 |
| rows | 预估扫描行数 | 越少越好 |
| filtered | 过滤后的行数百分比 | — |
| Extra | 额外信息 | ⭐ Using index(覆盖索引)/Using filesort(需优化)/Using temporary(需优化) |

**type 字段详解**（从优到差）：

| type | 说明 | 示例 |
|------|------|------|
| system | 系统表，只有一行 | — |
| const | 主键/唯一索引等值匹配，最多一行 | WHERE id = 1 |
| eq_ref | join 时驱动表的行在被驱动表用主键/唯一索引精确匹配 | join 主键 |
| ref | 非唯一索引等值匹配，可能多行 | WHERE name = '张三' |
| range | 索引范围扫描 | WHERE id > 10 |
| index | 全索引扫描（扫描整棵索引树） | SELECT id FROM t（覆盖索引） |
| ALL | 全表扫描 | 无索引可用 |

**Extra 常见值**：

| Extra | 含义 | 评价 |
|-------|------|------|
| Using index | 覆盖索引，不需要回表 | ✅ 很好 |
| Using where | Server 层有额外过滤 | 正常 |
| Using index condition | 索引下推（ICP） | ✅ 好 |
| Using filesort | 需要额外排序，没用上索引排序 | ⚠️ 需优化 |
| Using temporary | 使用了临时表 | ❌ 需优化 |
| Using join buffer | join 时没有索引，用了 Block Nested Loop | ❌ 需优化 |

#### 常见 SQL 优化手段

**1. 索引优化**
```sql
-- 避免全表扫描，确保 WHERE 条件走索引
-- 建立合适的联合索引，覆盖高频查询
-- 避免索引失效（函数/隐式转换/左模糊）
```

**2. JOIN 优化**
```sql
-- 小表驱动大表
-- 被驱动表的连接条件要有索引
-- 避免笛卡尔积
-- MySQL 优化器一般会自动选小表驱动，但 STRAIGHT_JOIN 可以强制指定
```

**3. 分页优化**
```sql
-- 深分页问题：LIMIT 1000000, 10 很慢
-- 原因：MySQL 需要扫描 1000010 行再丢弃前 1000000 行

-- 优化方案1：延迟关联（先查主键再回表）
SELECT * FROM user
INNER JOIN (SELECT id FROM user ORDER BY id LIMIT 1000000, 10) AS t
ON user.id = t.id;

-- 优化方案2：游标分页（记录上次最后一条的 id）
SELECT * FROM user WHERE id > last_max_id ORDER BY id LIMIT 10;
-- 要求主键有序且不能跳页
```

**4. COUNT 优化**
```sql
-- count(*) vs count(1) vs count(字段) vs count(id)
-- InnoDB 中 count(*) 和 count(1) 等价，都是遍历每一行判断非 NULL
-- count(字段) 会排除该字段为 NULL 的行
-- count(id) 如果有主键索引，比 count(*) 略快（不需要读数据页）
-- 性能：count(*) ≈ count(1) > count(id) > count(字段)

-- 大表 COUNT 优化：
-- 1. 单独维护计数表
-- 2. 缓存层（Redis）维护计数
-- 3. 允许近似值时用 SHOW TABLE STATUS 的 Rows 字段
```

**5. 大表优化**

| 方案 | 说明 | 适用场景 |
|------|------|---------|
| 读写分离 | 主库写，从库读 | 读多写少 |
| 分库分表 | 水平拆分（按 ID hash / 按时间） | 单表超千万行 |
| 归档历史数据 | 冷热分离，冷数据移到归档表 | 历史数据很少查询 |
| 索引优化 | 优化索引覆盖，减少回表 | 首选方案 |
| 缓存 | Redis 缓存热点数据 | 高并发读 |

### 问答实战（精讲及回答）

#### ⭐⭐⭐ EXPLAIN 的 type 字段有哪些值？分别什么意思？

**提问意图**：EXPLAIN 是 SQL 优化的起点，必须掌握。

**推荐回答**：

> EXPLAIN 的 type 字段表示 MySQL 访问数据的方式，从好到差依次是：
>
> system 是最好的，表示只查系统表，只有一行数据。const 表示通过主键或唯一索引等值匹配，最多返回一行，非常快。eq_ref 出现在 join 中，被驱动表用主键或唯一索引精确匹配驱动表的每一行，也是一对一的关系。
>
> ref 是通过非唯一索引等值匹配，可能返回多行。range 是索引范围扫描，比如 WHERE id > 10，只扫描索引的一部分。index 是全索引扫描，扫遍整棵索引树但不需要回表。ALL 是最差的，全表扫描，说明没有合适的索引。
>
> 优化的目标是至少达到 range 级别，一般要达到 ref。如果看到 ALL 就要考虑加索引或者改写 SQL。

#### ⭐⭐ 深分页怎么优化？

**提问意图**：实战问题，看有没有真正处理过大数据量分页。

**推荐回答**：

> MySQL 的 LIMIT offset, count 在 offset 很大时性能很差。比如 LIMIT 1000000, 10，MySQL 需要扫描 1000010 行数据，丢弃前 1000000 行，只返回 10 行。offset 越大越慢。
>
> 常用的优化方案有两种。第一种是延迟关联，也叫子查询优化。先用一个子查询只查主键（走覆盖索引，很快），LIMIT 1000000, 10 拿到 10 个 id，再用这 10 个 id 回主表 JOIN 拿完整数据。因为子查询只读主键索引页，IO 量小很多。
>
> 第二种是游标分页，也叫 keyset pagination。记录上一次查询最后一条记录的主键 id，下次查询用 WHERE id > last_id ORDER BY id LIMIT 10。这样每次都走主键索引范围扫描，不管第几页都是 O(1) 的效率。缺点是不能跳页，只能"下一页"。
>
> 实际项目中，如果业务上不需要跳页（比如无限滚动列表），游标分页是最佳方案。如果需要跳页，就用延迟关联来缓解。

#### ⭐ count(*) 和 count(1) 和 count(字段) 有什么区别？

**提问意图**：常见误区题，看理解精不精确。

**推荐回答**：

> 在 InnoDB 中，count(*) 和 count(1) 是完全等价的。MySQL 优化器会把 count(1) 优化成 count(*)。它们都是遍历每一行，判断行是否存在（不会真的去读某个字段的值），对于每一行都会加 1。
>
> count(字段) 则不同，它会判断该字段的值是否为 NULL，为 NULL 的行不计入。所以如果字段允许 NULL，count(字段) 的结果可能小于 count(*)。
>
> 性能方面，count(*) ≈ count(1) > count(主键) > count(普通字段)。count(*) 和 count(1) 最快是因为优化器不需要读取任何字段值。count(主键) 需要从索引中取出主键值判断非空（主键不可能为空，但还是会走取值流程，稍慢一点）。count(普通字段) 最慢，因为可能要回表读字段值并判断 NULL。
>
> 所以建议统一用 count(*)，语义清晰，性能最好。
