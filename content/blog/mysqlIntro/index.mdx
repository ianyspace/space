## 入门使用：把 SQL 写对、把表建好

### 一条 SQL 的一生

先建立一张地图。你在客户端敲下一条 SQL，它会穿过 MySQL 的两层结构：上面的 **Server 层**（连接器、分析器、优化器、执行器）负责流程控制，下面的**存储引擎层**（插件式，默认 InnoDB）真正负责存取数据。

<sql-arch-figure caption="MySQL 分层架构：Server 层管流程，InnoDB 管数据"></sql-arch-figure>

一条查询 SQL 按顺序经过这四站：

| 经过哪层 | 干什么 | 容易被问 |
| --- | --- | --- |
| 连接器 | TCP 握手、校验账号密码、分配连接 | **权限以「连上那一刻」为准**，中途改权限要重连才生效 |
| 分析器 | 词法分析（拆 token）+ 语法检查 | SQL 拼写错时那句 `You have an error in your SQL syntax` 就是这里报的 |
| 优化器 | 估算成本，选索引、定执行计划 | **索引用不用是优化器说了算**，不是你写了就一定走 |
| 执行器 | 先校验表级权限，再按计划逐行调用引擎接口 | 为什么权限检查不放连接器？——行级权限依赖执行上下文 |

把两个结论钉死：

- **索引用不用，是优化器说了算。** 它根据统计信息估算成本，你觉得该走的索引它可能不屑一顾——后面所有「索引失效」问题，根源都在这一层。
- **改数据比查数据多出来的，是三份日志。** undo log 记旧值、redo log 记改动、binlog 记操作。它们为什么必须存在、为什么提交顺序那么怪，见「三大日志与两阶段提交」。

另外两个小知识：查询缓存因为命中率太低在 **8.0 已被移除**；InnoDB 能胜出 MyISAM 靠的是三件事——支持事务、行级锁、崩溃后自动恢复（redo log），所以 5.5 起就是默认引擎，答题点出「MyISAM 不崩溃安全」即可。

### 库表设计的正确姿势

建表谁都会，考的是细节习惯。原则一句话：**够用的前提下越小越好，能整数就别字符串，金额绝不用浮点。**

```sql
CREATE TABLE `user` (
    `id`         BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT COMMENT '主键',
    `name`       VARCHAR(32)      NOT NULL DEFAULT '' COMMENT '用户名',
    `age`        TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '年龄',
    `phone`      CHAR(11)         NOT NULL DEFAULT '' COMMENT '手机号',
    `balance`    DECIMAL(12, 2)   NOT NULL DEFAULT 0 COMMENT '余额',
    `created_at` DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `updated_at` DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP
                                  ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_phone` (`phone`),
    KEY `idx_name` (`name`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '用户表';
```

每一行都对应一道小题：

| 选择 | 为什么 |
| --- | --- |
| 金额用 `DECIMAL`，不用 `FLOAT/DOUBLE` | 浮点数是二进制近似存储，`0.1 + 0.2 ≠ 0.3`，钱会算错；`DECIMAL` 精确 |
| 字符集用 `utf8mb4`，不用 `utf8` | MySQL 的 `utf8` 最多 3 字节，存不了 emoji（要 4 字节），插入会报错 |
| `CHAR(11)` 存手机号，`VARCHAR` 存长短不一的值 | `CHAR` 定长省去长度字节，适合几乎等长的值 |
| `TINYINT` 存年龄状态 | 1 字节够用；`INT` 4 字节是浪费 |
| 字段尽量 `NOT NULL DEFAULT ''` | `NULL` 让 `count(列)` 不统计它、参与比较永远为假，每行还要多 1 字节标记 |
| 主键自增 `BIGINT` | 自增保证顺序插入写入快（原因见「索引的底层：B+ 树」的页分裂）；`BIGINT` 上限足够业务用 |

**范式与反范式**的答题口径：范式（订单表只存 `user_id`）保证不冗余；反范式（订单表冗余一份下单时的 `user_name` 快照）用空间和一致性代价换查询性能。互联网业务读多写少，**适度冗余是常态**——但要说得出代价：「用户改名后，历史订单要不要跟着变？」能讲清这个权衡，比背三条范式加分。

### 索引使用入门

一句话定调：**索引 = 拿「写入变慢 + 占磁盘」换「查询飞快」的有序结构。** 建索引看查询来建：`WHERE`、`JOIN`、`ORDER BY` 里高频出现、区分度（不同值比例）高的列才值得建。它为什么时灵时不灵，答案全在底层结构里（见「索引的底层：B+ 树」）。

**联合索引的最左前缀原则**：把索引 `(name, age)` 想成字典排序——先按「姓」排，姓相同再按「名」排。

```sql
-- 假设有联合索引 (name, age)
WHERE name = '张三'                -- ✅ 用得上（先按姓查）
WHERE name = '张三' AND age = 25   -- ✅ 两列都用得上
WHERE name = '张三' AND city = '北京' -- name 用得上；city 与索引无关，段内过滤
WHERE age = 25                     -- ❌ 缺第一列，一列都用不上
```

断在中间（比如索引 `(a,b,c)` 只查 `a` 和 `c`）时，c 还能在 a 命中的段内当过滤条件；缺了第一列，就全废。

**索引失效的六个经典场景**，一张表记牢（共同点：让索引列失去有序性，或让优化器觉得不划算）：

| # | 场景 | 反例 | 为什么失效 | 怎么改 |
| --- | --- | --- | --- | --- |
| 1 | 对索引列做函数 / 运算 | `WHERE YEAR(created_at) = 2026` | 索引存的是原始值，函数结果无序，树无法定位，只能逐行算 | 改范围：`created_at >= '2026-01-01' AND created_at < '2027-01-01'` |
| 2 | 隐式类型转换 | `WHERE phone = 13800001234`（phone 是 VARCHAR） | 字符串列和数字比，等价于给每行套 `CAST(phone)`——就是场景 1 | 传字符串 `'13800001234'` |
| 3 | 前导模糊查询 | `WHERE name LIKE '%三'` | 开头未知，树定位不了起点 | `LIKE '张%'`（前缀确定才行） |
| 4 | 不满足最左前缀 | 索引 `(a,b,c)`，`WHERE b=1 AND c=2` | 跳过第一列，后面全无序 | 条件带上 a，或为该查询另建索引 |
| 5 | OR 一侧没索引 | `WHERE name='张三' OR address='北京'` | 一侧要全表扫，走索引那边省下的活白干 | 给 address 建索引，或改 `UNION ALL` 各走各的 |
| 6 | 优化器主动放弃 | `WHERE status = 1`（98% 的行都是 1） | **不是失效，是选择**：回表 98 万次不如全表扫 | 低区分度列（状态/性别）别单独建索引 |

判断到底用没用，用 `EXPLAIN`，重点看两列：**`type`**（访问方式，从好到差 `const > ref > range > index > ALL`，线上一般要求至少 `range`）和 **`key`**（实际用了哪个索引，`NULL` 就是没用上）。

**回表与覆盖索引**——InnoDB 里，二级索引的叶子只存「索引列 + 主键值」，主键索引（聚簇索引）的叶子才存整行。所以走二级索引查到主键后，往往还要回主键树再查一次：

<backtable-figure caption="回表：二级索引拿到 id，再回主键树取整行；覆盖索引免回表"></backtable-figure>

看图记住三句话：

1. `SELECT *` 几乎必然回表——要整行，二级索引里没有，这就是很多团队「禁止 SELECT *」的真正原因。
2. 查询要的列全在索引里（比如索引 `(name, age)` 查 `SELECT id, name, age`），就一次树查找收工，这叫**覆盖索引**。
3. 回表不是免费的：命中行很多时要回表几万次，优化器可能因此放弃索引改走全表扫描——「走索引不一定快」的分水岭就在这。

### 事务与隔离级别

ACID 四个特性都会背，真正有用的是从「不加隔离会出什么乱子」反推隔离级别。并发读写会出三种异常：

- **脏读**：读到别人**还没提交**的数据，对方随后回滚了——你基于一份数据库里从未存在过的数据做了决策。
- **不可重复读**：同一事务内两次读同一行，值不一样（中间被人 UPDATE 了）。针对**改**。
- **幻读**：同一事务内两次按同一条件统计，行数变了（中间被人 INSERT 了）。针对**插**。

四个隔离级别就是依次堵住这三种异常：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| READ UNCOMMITTED（读未提交） | ❌ 会发生 | ❌ 会发生 | ❌ 会发生 |
| READ COMMITTED（读已提交，RC） | ✅ 解决 | ❌ 会发生 | ❌ 会发生 |
| **REPEATABLE READ（可重复读，InnoDB 默认）** | ✅ 解决 | ✅ 解决 | ✅ 基本解决* |
| SERIALIZABLE（串行化） | ✅ | ✅ | ✅ 完全解决（读也加锁，并发最差） |

*「基本解决」是 MySQL 的独门考点，下面两张时间线表能看出「基本」两个字差在哪。把「事务 A」和「事务 B」想成两个终端窗口：

**剧本一：不可重复读**（B 改了数据并提交，A 前后读两次同一行）

| 步骤 | 动作 | RU | RC | RR | SER |
| --- | --- | --- | --- | --- | --- |
| 1 | A 开事务，第一次读 `balance` | 1000 | 1000 | 1000（同时生成快照） | 1000 |
| 2 | B 执行 `balance = 2000` 并提交 | — | — | — | 被 A 的锁挡住，要排队 |
| 3 | A 第二次读同一行 | **2000** ⚠️ | **2000** ⚠️ 不可重复读 | **1000** ✅ 读快照 | **1000** ✅ |

**剧本二：幻读**（B 插入了符合条件的新行，A 前后统计两次）

| 步骤 | 动作 | RU | RC | RR | SER |
| --- | --- | --- | --- | --- | --- |
| 1 | A 统计 `COUNT(*) WHERE age > 18` | 3 | 3 | 3（快照） | 3 |
| 2 | B 插入一行 `age = 20` 并提交 | — | — | — | 间隙锁挡住，插不进 |
| 3 | A 再统计一次 | **4** ⚠️ | **4** ⚠️ | **3** ✅（快照里没有） | **3** ✅ |
| 4 | A 执行 `UPDATE … WHERE age > 18`（当前读） | 影响 4 行 | 影响 4 行 | **影响 4 行** ⚠️ 快照看不到的那行，当前读写到了 | 影响 3 行 |

从表里读出三件事：

1. **RC 和 RR 的唯一本质区别**是：事务内第二次读时，能不能看到别人已提交的修改。RC 能（所以不可重复读），RR 不能（靠快照，见「MVCC：快照读是怎么实现的」）。
2. **RR 下普通 SELECT 看不到幻影行，但 UPDATE 这种当前读仍然改得到**——所以 InnoDB 的 RR 只是「基本」解决幻读，剩下的一半靠锁（见「锁体系：RR 下幻读是怎么被挡住的」）。
3. **SERIALIZABLE 最安全也最慢**：读也加锁，并发退化成串行，业务上很少用。脏读只在 RU 发生，业务上也没人用 RU。

使用层两条铁律：**事务尽量短**（事务里别放 RPC、发消息这类耗时操作，行锁攥在手里越久并发越差）；Java 里 `@Transactional` 默认只回滚 `RuntimeException`，受检异常要写 `rollbackFor = Exception.class`。

## 深入原理：InnoDB 的底牌

### 索引的底层：B+ 树

索引为什么快、为什么时灵时不灵，答案全在它的数据结构里。先想清楚约束条件：**数据在磁盘上，瓶颈不是比较次数，而是磁盘 I/O 次数**。磁盘一次读一页（InnoDB 固定 16 KB），我们希望一次 I/O 尽量多读有用的键、树尽量矮。拿候选结构挨个过：

| 结构 | 范围查询 | 定位效率 | 问题 |
| --- | --- | --- | --- |
| 哈希表 | ❌ 只能等值 | 等值 O(1) 很快 | 无法范围查询、无法排序，还有哈希冲突 |
| 红黑树 / 二叉搜索树 | ✅ | 百万行树高约 20 | 二叉太「瘦」：树高 ≈ I/O 次数，20 次随机 I/O 不可接受 |
| B 树 | ✅ | 矮 | 非叶子节点也存整行数据 → 单页装的键少、树反而更高；范围查询要来回上下穿梭 |
| 跳表 | ✅ | O(log n)，内存场景好手 | 磁盘场景每层一次随机 I/O；Redis 的 zset 用它（纯内存），数据库不用 |
| **B+ 树** | ✅ 叶子链表顺扫 | 千万行 3～4 层 | 磁盘场景的最优解 |

B+ 树的两个结构特点，把上面的劣势全部翻转：

1. **非叶子节点只存键（导航用），不存数据**——一页 16 KB 能塞上千个键，树的分叉（阶）极大，树极矮。
2. **数据全部在叶子节点，且叶子用链表串起来**——范围查询定位到左端点后顺着链表扫就行，不用回到上层。

下面的实验室可以亲手玩：插入看**分裂**、删除看**借位与合并**、查找看**路径**。

<b-plus-tree-lab caption="B+ 树实验室：插入看分裂，删除看借位与合并，查找看路径"></b-plus-tree-lab>

玩的时候对着看三个过程：

- **查找**：从根往下比较，每层只读一页（一次 I/O），到叶子链表上定位。
- **插入**：叶子满了就**分裂**成两页、把中间键上移给父节点「当路标」；父节点也满了就继续往上裂，裂到根就长高一层。
- **删除**：叶子里的键低于半满，先向左右兄弟**借位**，借不到才**合并**——所以删除比插入更少动结构。

**算一笔最爱考的账**：非叶子节点里，一个入口 = 主键 bigint（8 B）+ 页指针（6 B）= 14 B，一页 16 KB ÷ 14 B ≈ **1170 叉**；叶子节点按每行 1 KB 算，一页放 16 行。于是：

```text
高度 2（1 根 + 1170 个叶子）：1170 × 16          ≈ 1.9 万行
高度 3（1170 × 1170 个叶子）：1170 × 1170 × 16  ≈ 2190 万行
```

这就是「一张 2000 万行的表，B+ 树只要 3 层、一次主键查询最多 3 次页 I/O」的由来——根节点还常驻内存，实际更少。

这笔账还解释了**自增主键为什么重要**：叶子按主键有序，自增主键的新行永远追加到最后一页，页满了开新页就行；用 UUID 这类乱序主键，新行会随机插进某个页的中间，页满了就触发**页分裂**——把一半数据搬到新页，还要牵连更新父节点。写入越频繁，差距越大。所以一句话：**主键要「趋势递增」**，自增 or 雪花 ID 都行，UUID 不行。

### Buffer Pool：为什么快，为什么崩溃不丢

数据在磁盘上，但 InnoDB 绝不每次都碰磁盘——它把数据切成 16 KB 的**页**，用一块大内存缓存热页，这就是 **Buffer Pool**：

- **读**：先查 Buffer Pool，命中直接返回；命不中才把整页读进内存。
- **写**：**只改内存里的页**（变成「脏页」），绝不立刻写磁盘。

那磁盘上的旧数据怎么办？靠 **WAL（Write-Ahead Logging，先写日志再写数据）**：改动先**顺序写**进 redo log 并落盘，脏页由后台线程择机慢慢刷盘。磁盘上的数据页哪怕还是旧的，崩溃后重放 redo log 就能恢复。整个架构的支点就一句话：**顺序写日志永远比随机写数据页快**。

### MVCC：快照读是怎么实现的

MVCC（多版本并发控制）回答的问题是：**读写怎么互不阻塞？** 答案是给每行数据保留多个历史版本，读的人看「自己该看的版本」，不用等写的人。

两块拼图：

**① 版本链。** 每行数据有两个隐藏列：`trx_id`（最近一次修改它的事务 id）和 `roll_pointer`（指向上一个版本，旧版本存于 undo log）。一次次修改把版本串成链，新版本在头。

**② ReadView。** 事务做**快照读**（普通 `SELECT`）时拍一张「活跃事务名单」快照，四个字段：

| 字段 | 含义 |
| --- | --- |
| `m_ids` | 生成快照时还活跃（未提交）的事务 id 列表 |
| `min_trx_id` | `m_ids` 里最小的 |
| `max_trx_id` | 系统将分配给下一个事务的 id |
| `creator_trx_id` | 事务自己 |

拿到一个版本，判断逻辑只有四条：

```text
1. trx_id == creator_trx_id          → 可见（自己改的）
2. trx_id ∈ m_ids                    → 不可见（还没提交），顺链找上一版
3. trx_id < min_trx_id               → 可见（快照前就提交了）
4. trx_id ≥ max_trx_id               → 不可见（快照后才开启的事务）
   min ≤ trx_id < max 且不在名单里   → 可见（生成快照时已提交）
```

四条规则不难背，难的是在场景里用对。看这个经典场景：事务 A（trx_id=80）读一行，链上有三个版本；A 第一次读之后，B（trx_id=100）提交了。第二次读，RC 和 RR 会给出不同答案：

用表格逐版推演一遍，和图对照：

| 版本 | trx_id | RR：复用 ReadView①（m_ids=[90,100]） | RC：新建 ReadView②（m_ids=[90]） |
| --- | --- | --- | --- |
| v3 | 100 | 在活跃名单 → 不可见 | 不在名单（已提交）→ **可见 ✅ 读到 2000** |
| v2 | 90 | 在活跃名单 → 不可见 | 在活跃名单 → 不可见 |
| v1 | 60 | 60 < min(90) → **可见 ✅ 读到 500** | 轮不到它（v3 已命中） |

结论一句话：**RC 每次查询生成新 ReadView，RR 整个事务复用第一次的。** 「可重复读」不是什么神秘机制，就是「复用快照」四个字；「不可重复读」也就是「换了一张快照」。

还差最后一块：**当前读**。`UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 修改数据前必须看到最新已提交版本（总不能基于旧快照去改），所以它们不走 MVCC，而是**读最新版本 + 加锁**——这就是为什么「事务与隔离级别」的剧本二里，RR 挡住了快照读的幻读、却挡不住当前读。当前读的幻读要靠下一节的锁。

### 锁体系：RR 下幻读是怎么被挡住的

锁按粒度分三层，行级锁才是 InnoDB 的主场：

| 层级 | 锁 | 用途 |
| --- | --- | --- |
| 全局 | 全局锁（`FTWRL`） | 全库逻辑备份，库只读 |
| 表级 | 表锁、元数据锁（MDL）、**意向锁** | 意向锁：加行锁前先在表上打标记，让「要不要锁全表」的判断不用逐行扫 |
| 行级 | 记录锁、间隙锁、临键锁 | 下面细说 |

行级锁的三种形态，针对 B+ 树上「锁什么」：

- **记录锁（Record Lock）**：锁住索引上的一条记录。
- **间隙锁（Gap Lock）**：锁住两条记录之间的**开区间空隙**，比如 `(10, 20)`——不许别人往里插新行。它**只堵插入**，彼此不冲突：两个事务可以同时持有同一个间隙的间隙锁。
- **临键锁（Next-Key Lock）**：记录锁 + 前面的间隙，左开右闭区间 `(10, 20]`。**RR 级别下，当前读的默认加锁单位就是临键锁**，这就是 RR 挡住当前读幻读的机制。

以 `SELECT * FROM t WHERE id > 10 AND id < 20 FOR UPDATE` 为例（id 有索引，表里有 …10、20…）：InnoDB 会锁住 `(10, 20]` 这个临键区间，另一个事务想 `INSERT` 一个 `id = 15`，插入意图落进被锁的间隙，阻塞——幻读被挡住。

三个初中级必知的坑：

- **锁是加在索引上的。** 当前读的条件没走索引，就只能逐行扫全表、把所有记录都锁住，等效锁全表。这也是「UPDATE 一定要走索引」的真正原因。
- **间隙锁在 RC 级别不存在**（RC 只有记录锁），这是很多公司用 RC 的原因之一：锁更少、并发更好、死锁更少，代价是幻读和不可重复读回来了——业务自己保证。
- **经典死锁**：事务 A 和 B 先后对同一间隙持有间隙锁（间隙锁互相兼容），然后 A 想 `INSERT`、B 也想 `INSERT`，各自的插入意向锁都被对方的间隙锁堵住——互相等待，死锁。InnoDB 会自动检测并回滚代价小的事务，但**尽早在事务开头一次性锁住需要的资源**才是根治办法。

### 三大日志与两阶段提交

三种日志各司其职，先分清：

| 日志 | 所在层 | 类型 | 记录什么 | 给谁用 |
| --- | --- | --- | --- | --- |
| undo log | InnoDB | 逻辑 | 反向操作（旧值） | 回滚、MVCC 的版本链 |
| redo log | InnoDB | 物理 | 「某页某处改成了什么」 | 崩溃恢复（保证持久性） |
| binlog | Server | 逻辑 | 「执行了什么语句/行变化」 | 主从复制、按时间点恢复 |

redo 是 InnoDB 私有的**循环写**日志（写满就阻塞，等后台刷脏页腾位置）；binlog 是**追加写**的归档日志。为什么必须两个都有？——redo 只对本实例恢复有用且会被覆盖，主从复制和「恢复到昨天三点」必须靠 binlog。

问题来了：一份改动要写两个日志，**写完一个、还没写另一个就宕机呢？** 解法就是**两阶段提交（2PC）**：redo 先置 `prepare` → 写 binlog → redo 置 `commit`。一条 UPDATE 的完整顺序：

<log-figure caption="一条 UPDATE 的完整落盘顺序：三份日志 + 脏页，谁先谁后"></log-figure>

图中三个断电点，恢复结果各不相同——拿 binlog 当仲裁：**binlog 完整就提交，不完整就回滚**：

| 断电时刻 | redo 状态 | binlog | 恢复规则 | 最终结果 |
| --- | --- | --- | --- | --- |
| A：写完 undo，还没写 redo | 空 | 空 | 无需恢复 | 数据原样（1000） |
| B：redo 已 prepare，binlog 未写 | prepare | 未写 | binlog 不完整 → 回滚 | 回到 1000，主从一致 |
| C：binlog 已写，redo 还是 prepare | prepare | 完整 | binlog 完整 → 补提交并重放 redo | 1100，主从一致 |
| 提交后任意时刻（含返回 OK 后、刷脏页前） | commit | 完整 | 直接重放 redo | 1100（脏页没刷也不怕） |

为什么必须是这个顺序？反着想就明白了：若「先 redo 后 binlog」，redo 落盘后宕机——主库恢复出这条数据、binlog 里却没有，**从库少一条**；若「先 binlog 后 redo」，binlog 落盘后宕机——主库回滚了、从库却回放了，**从库多一条**。只有两阶段提交能让崩溃恢复时拿 binlog 做仲裁，两边永远对得上。而 undo log 全程兜底：「没提交的修改全部回滚」就是原子性 A 的实现。

## 问答实战

答题心法：初中级考的不是背诵，是**「现象 → 机制 → 代价」**三层。每题先给结论，再讲机制，最后主动提一句代价或权衡，就是完整的好回答。

### 索引与 B+ 树

**Q：为什么用 B+ 树而不是哈希表 / B 树 / 红黑树 / 跳表？**

按对比表答：哈希只能等值；红黑树百万行高约 20，I/O 太多；B 树非叶子也存数据，单页键少树更高、范围查询要上下穿梭；跳表是内存好手（Redis zset 用它），磁盘场景每层一次随机 I/O。B+ 树非叶子只存键 → 一页上千键 → 极矮；叶子链表 → 范围顺扫。

**Q：一张 2000 万行的表，B+ 树多高？一次查询几次 I/O？**

现场算账：16 KB ÷ (8 B 键 + 6 B 指针) ≈ 1170 叉；叶子按 1 KB/行放 16 行；1170 × 1170 × 16 ≈ 2190 万 → **3 层，最多 3 次页 I/O**，根常驻内存实际更少。这题背不出数字就现推，提问者想看的就是推导过程。

**Q：为什么推荐自增主键？UUID 为什么不行？**

自增 = 新行永远追加到最后一页；UUID 乱序 = 随机插进页中间 → 页分裂（搬一半数据到新页 + 牵连父节点）→ 写入变慢、页空间利用率低。补一句「趋势递增即可，雪花 ID 也行」更完整。

**Q：什么是回表？什么是覆盖索引？怎么避免回表？**

先答机制：二级索引叶子存「索引列 + 主键」，要整行就回主键树再查一次；覆盖索引 = 查询列全在索引里，免回表。再给方案：把高频查询列加进联合索引。最后补一句代价：索引不是白加的，写入变慢、占空间。

**Q：联合索引 (a, b, c)，WHERE b = 1 AND c = 2 能用到索引吗？ORDER BY a 呢？**

不能定位，`type=ALL`（缺 a）；`ORDER BY a` 也用不上（a 在索引里整体无序）。但 `WHERE a = 1 ORDER BY b` 是经典好题：a 定位后，a 相同的段内 b 有序，排序直接免掉（`Extra: Using index` 而不是 `Using filesort`）。

**追问链示范**：为什么索引列上用函数会失效？→ 索引存的是原始值，函数结果无序无法定位。→ MySQL 8.0 有没有解？→ 函数索引（对表达式的结果建索引）。→ 隐式类型转换为什么失效？→ 等价于对每行的列做 CAST，同一类问题。

### 事务与 MVCC

**Q：隔离级别有哪些？InnoDB 默认是哪个？它解决了什么？**

先背现象层：四个级别与脏读 / 不可重复读 / 幻读的对应表；然后主动升华：InnoDB 默认 RR，快照读靠 MVCC 解决，当前读靠临键锁把幻读也基本挡住了——这句是和普通候选人的分水岭。

**Q：MVCC 的实现原理？**

按「MVCC：快照读是怎么实现的」的顺序答：隐藏列（`trx_id` + `roll_pointer`）→ undo log 版本链 → ReadView 四字段 → 四条可见性规则 → 「RC 每次查询新建 ReadView，RR 复用第一次的」收尾。全流程一分钟，信息密度拉满。

**Q：RR 下的幻读真的解决了吗？**

标准答案：没有完全解决。快照读靠 MVCC 看不见幻影；但当前读（`UPDATE` / `FOR UPDATE`）能看到最新提交的数据，先查后改就可能「见鬼」。InnoDB 用间隙锁 / 临键锁堵住当前读的插入，但间隙锁互相兼容反而引入死锁风险——所以严格说是「基本解决」。

### 锁类

**Q：InnoDB 有哪些锁？**

按粒度答：全局锁、表级（表锁 / MDL / 意向锁）、行级（记录锁 / 间隙锁 / 临键锁）。点出意向锁的作用（表级标记，避免判断表锁时逐行扫）就是加分项。

**Q：UPDATE 没走索引会发生什么？**

加锁范围从行锁膨胀到近似锁全表（逐行扫全锁），并发直接归零。所以「写操作必须走索引」不是性能问题，是可用性问题。

**Q：说说一个你遇到的死锁场景，怎么解决？**

「锁体系：RR 下幻读是怎么被挡住的」里那个间隙锁死锁就是标准素材：两个事务共享间隙锁后互相插入被堵。解决：统一加锁顺序、事务尽量短、一次性锁齐资源、必要时降级 RC 去掉间隙锁。

### 日志与优化类

**Q：redo log 和 binlog 的区别？为什么需要两阶段提交？**

先对比表（层、类型、写入方式、用途），再讲不一致场景（先写 redo 宕机 → 主有从无；先写 binlog → 从有主无），最后落回 2PC 的仲裁规则：「binlog 完整则提交，否则回滚」。三层都答到，这题就封顶了。

**Q：一条 SQL 很慢，怎么排查？**

给出可执行的流程：`EXPLAIN` 看 `type`（有 `ALL` 先解决索引）和 `rows`（扫描量）→ 检查是否踩失效场景（函数、隐式转换、前导 `%`）→ 大分页 `LIMIT 100000, 20` 改延迟关联 / 游标 → 仍慢就考虑数据量（归档、分表）。答到「先测量再优化」的意识就赢了大多数背题的。
