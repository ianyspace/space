## 一、MQ 到底是什么

先摆清角色，后面所有名词都挂在这三个角色上：

| 角色 | 干什么 | 典型代表 |
| --- | --- | --- |
| 生产者 Producer | 把消息发到 Broker | 订单服务、网关 |
| Broker（消息队列本体） | 把消息**存下来**，再**投出去** | Kafka / RocketMQ / RabbitMQ |
| 消费者 Consumer | 拉取并处理消息 | 积分服务、短信服务、数据平台 |

一句话定义：**MQ 是一个「先存后转」的中间层**。生产者只管把消息交给它，不关心谁消费、什么时候消费。

> 快递站类比：寄件人（生产者）放下包裹就走，快递站（Broker）负责存放和分拣，收件人（消费者）什么时候来取都行。
> 「站」这个中间环节，就是解耦发生的地方。

## 二、为什么用它：异步、解耦、削峰

三大作用听着抽象，最好的理解方式是**把开关拨到另一侧看对比**。下面这张图有三个标签页，切换按钮会重播动画：

<mq-roles-demo caption="MQ 的三大作用：亲眼看一遍对比"></mq-roles-demo>

### 2.1 异步：把「等待」换成「通知」

下单要扣库存、加积分、发短信、写统计。同步调用意味着用户要等全部做完；接上 MQ，主链路只做「校验 + 发消息」，剩下的交给消费者并行处理。

响应时间从「所有步骤之和」变成「最慢的那一步」——图里是 300ms 变成 35ms。

### 2.2 解耦：从网状调用到星型

直连时，订单服务要知道每个下游的地址、协议、超时和重试策略；加一个下游就要改它一次、发布一次。换成 MQ 之后，订单服务只认识一个 Topic，下游自己订阅、自己扩容、自己换语言。

### 2.3 削峰：把洪峰存进队列

下游只有 1000 QPS 的处理能力，秒杀瞬间进来 6000 QPS。没有 MQ，多出来的 5000 只能超时或拒绝；有 MQ，全部收下先排队，下游按自己的节奏匀速消费。

积压的恢复时间可以粗略估算（$|B|$ 是积压量，$C$ 是消费能力）：

$$
T_{\text{清空}} \approx \frac{|B|}{C}
$$

图里积压峰值 1.2 万条、消费能力 1000 QPS，就需要再花约 12 秒才追平——**这段时间下游依然是满负荷，而且队列还在占磁盘**。

### 2.4 代价：MQ 不是银弹

| 付出什么 | 具体表现 | 怎么缓解 |
| --- | --- | --- |
| 一致性变弱 | 用户看到「下单成功」时，积分可能还没到账 | 最终一致 + 对账 + 补偿任务 |
| 系统更复杂 | 多了 Broker 要运维、要监控、要容量规划 | 用托管服务 / 统一中间件团队 |
| 可用性风险 | MQ 挂了，主链路也可能挂 | 降级开关、本地消息表、集群部署 |
| 问题更难查 | 消息丢了、重复了、顺序乱了，链路长 | 全链路 traceId + 消息轨迹 + lag 监控 |

## 三、附带一问：为什么 MQ 能这么快

面试常接着问「Kafka 为什么吞吐这么高」。答案不是单个魔法，而是四件事叠加：

1. **顺序写磁盘**：消息只追加、不修改，写盘退化成顺序 I/O，比随机写快几个数量级；
2. **页缓存 + 刷盘策略**：先写操作系统的 page cache，再由后台批量刷盘，兼顾速度与持久性；
3. **零拷贝**：消费时用 `sendfile` 把数据从页缓存直接送到网卡，省掉「内核 → 用户态 → 内核」的两次拷贝；
4. **批量 + 分区并行**：生产者批量发送、Broker 批量落盘、多个分区天然并行，吞吐随分区数横向扩展。

> 一句话：**把随机写变成顺序写，把多次拷贝变成零拷贝，再把单线程变成多分区并行。**

## 四、主流 MQ 怎么选

| 维度 | Kafka | RocketMQ | RabbitMQ |
| --- | --- | --- | --- |
| 定位 | 流平台 / 日志管道 | 业务消息（阿里系） | 传统企业消息（AMQP） |
| 单机吞吐 | 十万级 | 十万级 | 万级 |
| 延迟 | 毫秒级（批量下更高） | 毫秒级 | 微秒～毫秒，最低 |
| 顺序消息 | 分区内有序 | 支持分区顺序，且专门实现 | 队列内有序 |
| 事务 / 延迟消息 | 事务有，延迟消息弱 | 事务消息、任意延迟消息 | 靠插件或 TTL + DLX |
| 重试 / 死信 | 需自行实现 | 内置重试 + 死信队列 | 内置 DLX |
| 典型场景 | 日志、埋点、流计算、大数据管道 | 电商交易、订单、支付 | 中小规模业务解耦、任务分发 |

选型口诀：**日志与大数据选 Kafka，交易类业务选 RocketMQ，中小规模求简单可靠选 RabbitMQ**。真正难的不是选，而是把「丢消息、重复、顺序、积压」这四件事在设计阶段就想清楚。

## 五、名词速查表

| 名词 | 一句话解释 |
| --- | --- |
| Topic | 消息的逻辑分类，比如 `order-created` |
| Partition / Queue | Topic 的物理分片，**并行度与顺序性的基本单位** |
| Offset（位点） | 消费者在分区里的消费进度，提交早了会丢、提交晚了会重 |
| Consumer Group | 消费组。组内一条消息只给一个消费者，组间互不影响（广播靠不同组） |
| Broker | 消息存储与投递的服务器，一个集群由多个 Broker 组成 |
| ISR | 与 leader 保持同步的副本集合，副本机制决定「宕机丢不丢」 |
| ACK | 确认。生产者确认管「发出去没」，消费者确认管「处理完没」 |
| 死信队列 DLQ | 重试耗尽后的兜底去处，需要人工或定时任务处理，且必须告警 |
| Lag / 堆积量 | 还没被消费的消息数，是 MQ 最重要的监控指标 |

## 六、一条消息的一生

概念背完了，来看它真正怎么走。下面这张图可以**单步、也可以自动播放**，还能切换「正常 / 消费失败 / 发送失败」三个场景：

<mq-delivery-demo caption="一条消息的一生（可单步 / 自动播放）"></mq-delivery-demo>

把上面八步压缩成一句话：**生产者发 → Broker 存 → 消费者拉 → 处理完 → 提交位点**。中间每一步都可能出问题，所以每一步都要有保护：

| 环节 | 可能出的事 | 保护手段 |
| --- | --- | --- |
| 生产者 → Broker | 网络抖动、Broker 选主，消息没发出去 | 同步确认（`acks=all`）+ 重试 + 本地消息表 |
| Broker 存储 | 断电、磁盘损坏、副本没同步 | 同步刷盘 + 副本数 ≥ 2 + 主从切换 |
| Broker → 消费者 | 处理到一半宕机、位点提交错了 | 处理完再 ACK + 消费端幂等 |
| 消费之后 | 重试到上限仍在失败 | 死信队列 + 告警 + 人工/定时补偿 |

### 6.1 投递语义：三种，但工程上只一种常用

| 语义 | 怎么做到 | 结果 |
| --- | --- | --- |
| 最多一次 At most once | 先提交位点，再处理 | 快，但可能丢 |
| 至少一次 At least once | 先处理，成功后再提交位点 | 不丢，但可能重复（**默认选择**） |
| 精确一次 Exactly once | 事务 / 幂等生产者 + 消费端幂等 | 代价高，且通常只在 MQ 内部成立 |

面试要点：Kafka 的 exactly-once（幂等生产者 PID + 序列号，跨分区靠事务）解决的是**Kafka 内部**的重复；一旦你要写 MySQL、调第三方接口，「精确一次」就落回到 **至少一次 + 业务幂等**。

## 七、消息丢了怎么办：三个环节挨个堵

丢消息永远是这三问：**生产者发出去了吗？Broker 存住了吗？消费者处理完了吗？**

下面这个实验可以给每个环节注入故障，看结论怎么变——试试点「经典踩坑配置」：

<mq-reliability-demo caption="消息会丢在哪一环？（可注入故障）"></mq-reliability-demo>

### 7.1 生产者：确认 + 重试 + 兜底

```java
// RocketMQ：必须拿到 SEND_OK 才算成功，失败要有兜底，而不是只打一行日志
SendResult result = producer.send(message, 3000);
if (result.getSendStatus() != SendStatus.SEND_OK) {
    messageRepository.save(orderId, payload); // 落本地消息表，交给定时任务补偿
}
```

```java
// Kafka：acks=all + retries + 幂等生产者（都在配置里给）
producer.send(new ProducerRecord<>("order-created", orderId, json), (metadata, ex) -> {
    if (ex != null) {
        messageRepository.save(orderId, json); // 发送失败 → 兜底补偿
    }
});
```

关键配置：`acks=all`（所有 ISR 副本确认）、`min.insync.replicas>=2`、`retries>0`、`enable.idempotence=true`。
注意 **`acks=1` 是不够的**：leader 写成功就返回，leader 立刻挂掉就会出现「生产者以为成功、消息却没了」。

### 7.2 Broker：刷盘 + 副本

- **刷盘**：同步刷盘（写盘成功才回 ACK）不丢但慢；异步刷盘（写页缓存就回 ACK）快，但机器断电会丢。
- **副本**：副本数 ≥ 2，并禁止 `unclean.leader.election`（否则落后的副本被选为 leader，会直接丢数据）。
- **权衡**：把「不丢」和「高吞吐」都做到极致不可能，业务消息用同步刷盘更稳，日志类用异步刷盘换吞吐。

### 7.3 消费者：先处理，后 ACK

顺序绝对不能反：**位点提交早了 = 直接丢**。

```java
@KafkaListener(topics = "order-created", groupId = "points-group")
public void onMessage(ConsumerRecord<String, String> record, Acknowledgment ack) {
    OrderMessage msg = parse(record.value());

    if (dedup.notExists(msg.getId())) { // 幂等：处理过就跳过，避免重复加积分
        pointsService.add(msg.getUserId(), msg.getPoints());
        dedup.save(msg.getId());
    }

    ack.acknowledge(); // 处理完才提交位点，顺序错了就是丢消息
}
```

（Spring Kafka 需要 `spring.kafka.listener.ack-mode=manual_immediate`；RocketMQ 的 Listener 则是「正常返回即 ACK、抛异常即重试」，规则不同但原理一致。）

## 八、消息重复怎么办：做幂等

「不丢」和「不重」通常只能二选一。选了至少一次，就一定会收到重复消息——**重复消息不是异常，是正常流量**，所以消费端必须幂等。

| 方案 | 做法 | 适用场景 |
| --- | --- | --- |
| 唯一索引 | 用消息 ID / 业务唯一键建唯一索引，插入冲突即视为已处理 | 落库类操作，**最可靠、首选** |
| 状态机 | 只允许单向流转（待支付 → 已支付），重复消息被状态判断挡掉 | 订单、支付等有状态业务 |
| Redis 去重 | `SETNX messageId` 加过期时间 | 高频场景，可容忍极小概率失效 |
| 版本号 / CAS | `UPDATE ... WHERE version = ?` | 更新类操作 |

> 一个容易踩的坑：**重试本身就会产生重复**。第一次其实已经处理成功，只是确认丢了，重试再来一遍。所以幂等的判断必须放在「业务处理之前、和业务同一个事务里」。

## 九、顺序消息：怎么保证、代价是什么

**结论：MQ 只保证「分区内有序」，不保证「全局有序」。** 想有序，就要把有序范围缩小到同一个 key。

| 要点 | 说明 |
| --- | --- |
| 怎么确保同 key 有序 | Kafka 用 key 的 hash 路由到固定分区；RocketMQ 用顺序消息 + 队列选择器 |
| 为什么分区内就有序 | 一个分区在同一消费组内只由一个消费者消费，天然串行 |
| 消费端还要注意什么 | 分区必须**单线程**消费，扔进线程池并发处理立刻丢顺序 |
| 代价 | 单 key 吞吐 = 单分区能力；消费失败会阻塞后面的消息（RocketMQ 顺序消息会一直重试） |
| 全局有序 | 只能单分区，吞吐牺牲巨大，一般只在极小数据量下用 |

面试高频追问：「为什么顺序消息不能走普通重试？」——因为普通重试会把失败消息丢到重试队列（TOPIC_RETRY_QUEUE），
重新投回来后顺序就乱了，所以顺序消息必须原地阻塞重试。

## 十、消息积压：四步急救

积压（lag 持续上涨）是线上最常见的 MQ 事故，处理顺序不要乱：

1. **先定位**：是流量突增，还是消费变慢？看 lag 曲线、单条处理耗时、下游 RT、慢 SQL。
2. **横向扩**：消费者数 < 分区数就加消费者；已经相等就先加分区（注意分区只能增不能减），再加消费者。
3. **优化单条耗时**：批量拉取（`max.poll.records`）、批处理落库、把同步 RPC 改异步、去掉不必要的序列化。
4. **兜底**：临时扩容、把积压消息转存到临时 Topic 分流、非核心消息降级丢弃，并**保留重置位点的能力**作为最后手段。

> 记住两个数字：并行度上限 = 分区数；清空时间 ≈ 积压量 ÷ 消费能力。扩容前先算一算，别拍脑袋。

## 十一、分区、消费组与重平衡

这张图能动手：发消息、加消费者、让消费者宕机、改分区数，观察分区怎么分、谁闲着：

<mq-partition-demo caption="分区、消费组与重平衡：动手试试"></mq-partition-demo>

三个必考结论：

- **同一 key 永远进同一分区**，所以「同 key 有序」是路由带来的，不是 MQ 额外做了什么；
- **一个分区在同一个消费组内只由一个消费者消费**，所以并行度上限就是分区数，消费者再多也白搭；
- **任何成员变化（上线、下线、订阅变更、分区变化）都会触发重平衡**，期间消费短暂停止，这也是「消费者扩容反而抖动」的原因。

> 另一个坑：消费位点是**按分区记录**的，重平衡会把分区整体交给新消费者，所以「消费者数」这个参数并不影响消息是否重复，
> 真正影响的是你什么时候提交位点。

## 十二、事务消息：跨服务的最终一致性

本地事务和发消息没法放在一个事务里，于是有了两种典型做法：

**做法一：本地消息表**（通用，任何 MQ 都能用）。业务和「待发送消息」写进同一个本地事务，后台任务扫描后投递，失败的继续重试。

**做法二：RocketMQ 事务消息**（把回查交给 Broker）：

1. 生产者发送 **half 消息**（存在 Broker 里，但消费者不可见）；
2. Broker 落盘成功，返回确认；
3. 生产者执行**本地事务**（扣款、创建订单）；
4. 本地事务成功 → 回 `COMMIT`，消息可见；失败 → 回 `ROLLBACK`，消息删除；
5. 如果生产者没回结果（进程挂了），Broker 会**定时回查**，生产者检查本地事务状态后补回结果。

两者要解决的问题完全一样：**别让「业务成功但消息没发」和「消息发了但业务回滚」发生**。区别只是回查由谁来做。

## 十三、面试速查：15 问

| 问题 | 一句话答案 |
| --- | --- |
| 为什么要用 MQ？ | 解耦、异步、削峰；代价是一致性变弱、系统变复杂、MQ 本身成为可用性风险。 |
| Kafka 为什么快？ | 顺序写 + 页缓存 + 零拷贝 + 批量 + 分区并行。 |
| 怎么保证消息不丢？ | 生产者确认、Broker 刷盘与多副本、消费者处理完再 ACK，三环缺一不可。 |
| 消息重复了怎么办？ | 幂等：唯一索引优先，配状态机 / Redis 去重；「至少一次」是默认语义。 |
| 三种投递语义？ | 最多一次（可能丢）、至少一次（可能重，**常用**）、精确一次（代价高，且通常只在 MQ 内部成立）。 |
| 怎么保证顺序？ | 同 key 进同分区，分区内单线程串行消费；全局有序只能单分区。 |
| 消费者比分区多会怎样？ | 多出来的闲着，并行度上限是分区数。 |
| 什么时候会 rebalance？ | 成员增减、订阅关系变化、分区数变化；期间消费暂停。 |
| 积压了怎么处理？ | 先定位瓶颈，再扩消费者/扩分区，然后优化单条耗时，最后才考虑分流或降级。 |
| 三者怎么选？ | 日志大数据 Kafka、交易业务 RocketMQ、中小规模求简单 RabbitMQ。 |
| 分区是不是越多越好？ | 不是：顺序性更差、句柄与内存开销更大、rebalance 更慢、下游压力更大。 |
| RocketMQ 事务消息原理？ | half 消息 + 本地事务 + 定时回查，保证「业务与消息」最终一致。 |
| 位点（offset）是什么？ | 消费进度。提交早了会丢消息，提交晚了会重复消费。 |
| 死信队列有什么用？ | 兜住重试耗尽的消息，必须配告警和人工/定时处理，否则等于没处理。 |
| MQ 挂了业务还能用吗？ | 看设计：本地消息表 + 降级开关 + 集群部署，别让 MQ 成为单点。 |

## 十四、小结

| 主题 | 一句话记忆 |
| --- | --- |
| 作用 | 异步、解耦、削峰，换来最终一致与更高复杂度 |
| 生命周期 | 生产者发 → Broker 存 → 消费者拉 → 处理完 → 提交位点 |
| 不丢 | 生产者确认、Broker 刷盘多副本、消费者手动 ACK，三环全开 |
| 不重 | 至少一次 + 消费端幂等，重复是正常流量 |
| 有序 | 同 key 同分区 + 单线程消费，代价是单 key 串行 |
| 积压 | 清空时间 ≈ 积压量 ÷ 消费能力，扩容前先算账 |

最后再玩一遍完整流程，这次留意三件事：**位点在哪一步提交**、**失败时消息停在哪个节点**、**副本这一环少了会怎样**。
