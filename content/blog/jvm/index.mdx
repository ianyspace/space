## JVM 内存结构（运行时数据区）

### 基础概念

JVM 在运行 Java 程序时，会把管理的内存划分为若干个不同的数据区域。这些区域统称为 **运行时数据区**。

| 线程私有 | 线程共享 |
|---------|---------|
| 程序计数器 | 堆（Heap） |
| 虚拟机栈 | 方法区（Method Area）—— JDK 7 及以前是永久代（PermGen），JDK 8+ 改为元空间（Metaspace） |
| 本地方法栈 | |

> **快速记忆**：堆堆栈，两栈一计数，堆和方法区共享。

### 原理深入

#### 程序计数器（Program Counter Register）

- 每个线程独有一份，记录当前线程正在执行的字节码指令地址
- 如果线程执行的是 Native 方法，计数器的值为空（Undefined）
- **唯一不会 OOM 的内存区域**

#### 虚拟机栈（Java Virtual Machine Stack）

每个线程创建时分配一个虚拟机栈，栈内部以 **栈帧** 为基本单位：

```text
虚拟机栈（线程独占）
    │
    ├── 栈帧 N（当前方法）
    │   ├── 局部变量表（Local Variables）
    │   │   └── 存放方法参数、局部变量。基本类型存值，引用类型存堆地址
    │   ├── 操作数栈（Operand Stack）
    │   │   └── 字节码指令执行时的操作栈，如 iadd 弹出两个数相加再压入
    │   ├── 动态链接（Dynamic Linking）
    │   │   └── 指向运行时常量池中该方法对应的符号引用
    │   └── 方法返回地址（Return Address）
    │
    ├── 栈帧 N-1（调用者）
    └── ...
```

**两种异常**：

- `StackOverflowError`：栈深度超过限制（通常递归太深）
- `OutOfMemoryError`：栈扩展时无法申请到足够内存

#### 本地方法栈（Native Method Stack）

- 与虚拟机栈类似，但服务的是 **Native 方法**
- HotSpot 把虚拟机栈和本地方法栈合二为一

#### 堆（Heap）

| 区域 | 占比 | 细分 |
|------|------|------|
| 新生代（Young Generation） | 约 1/3 | Eden 约 8/10，Survivor 0（S0）/ Survivor 1（S1）各约 1/10 |
| 老年代（Old / Tenured Generation） | 约 2/3 | 长期存活的对象 |

**对象分配流程**：

1. 新对象优先在 Eden 区分配
2. Eden 满触发 Minor GC，存活对象进入 S0
3. 每次 Minor GC，S0 ↔ S1 交替，对象年龄 +1
4. 年龄达到阈值（默认 15）或 Survivor 放不下，进入老年代
5. 老年代满触发 Major GC / Full GC

**TLAB（Thread Local Allocation Buffer）**：多线程并发分配对象时需要同步，TLAB 给每个线程在 Eden 区预分配一块私有缓冲区，减少锁竞争。

#### 方法区 / 元空间

| 对比项 | 永久代（JDK 7 及以前） | 元空间（JDK 8+） |
|--------|------------------------|-------------------|
| 存放位置 | JVM 堆内 | 本地内存（Native Memory） |
| 大小限制 | `-XX:MaxPermSize` | `-XX:MaxMetaspaceSize`（默认无限制） |
| 类卸载 | 条件苛刻，容易 OOM | 自动回收，Full GC 触发 |
| 存储内容 | 类信息、常量、静态变量 | 类信息、常量（静态变量移到堆） |

**方法区存什么**：

- 类的完整信息（版本、字段、方法、接口）
- 运行时常量池（字面量和符号引用）
- JIT 编译后的代码缓存

### 问答实战（精讲及回答）

#### ⭐⭐ 说一下 JVM 内存模型，哪些是线程共享的？

**提问意图**：基础必考题，考察对 JVM 结构有没有清晰的认识。

**推荐回答**：

> JVM 内存分五块：程序计数器、虚拟机栈、本地方法栈、堆和方法区。
>
> 线程私有的三块：程序计数器记录当前指令地址，虚拟机栈存储方法调用栈帧，本地方法栈服务 Native 方法。
>
> 线程共享的两块：堆存放所有对象实例和数组，是 GC 的主战场；方法区存类信息、运行时常量池和编译后的代码。JDK 8 用本地内存中的元空间替代了堆内的永久代。
>
> 其中唯一不会 OOM 的区域是程序计数器。

**追问准备**：

- "为什么去永久代？" → 永久代受 `-XX:MaxPermSize` 限制，大量动态加载类容易 OOM。元空间使用本地内存，仅受系统实际内存限制。另外，永久代回收条件苛刻，类卸载困难。

---

#### ⭐⭐⭐ 一个对象从创建到进入老年代，经历了什么？

**提问意图**：考察对堆分代结构和 GC 过程的理解深度。

**推荐回答**：

> 优先在 Eden 区分配（有 TLAB 就先在私有缓冲区分配）。Eden 区快满时触发 Minor GC，存活的对象被复制到 S0，年龄标记为 1。之后每次 Minor GC，存活对象在两个 Survivor 区之间辗转，年龄累加。达到 `-XX:MaxTenuringThreshold` 默认值 15 后，晋升到老年代。
>
> 两个特殊情况也会提前晋升：一是 Survivor 区放不下——存活对象太多直接进老年代（空间担保）；二是大对象，超过 `-XX:PretenureSizeThreshold` 的大对象直接进老年代，避免在 Survivor 区无谓拷贝。

**追问准备**：

- "为什么不把年龄阈值设大一些？" → 阈值越小，老年代堆积越快，Full GC 频率升高。但阈值太大，对象在 Survivor 区反复拷贝也浪费性能。15 是 GC 根集合大小的平衡点。

---

#### ⭐⭐ 什么是栈帧？里面有什么？

**提问意图**：考察对方法调用底层机制的理解。

**推荐回答**：

> 每个方法调用对应一个栈帧压入虚拟机栈，方法返回时栈帧出栈。栈帧包含四部分：局部变量表存放方法参数和局部变量（基本类型存值、引用类型存堆地址）；操作数栈是字节码执行的操作空间，比如加法指令会弹出两个数相加再压回；动态链接指向运行时常量池中该方法对应的符号引用；方法返回地址记录调用者的 PC 值以便恢复执行。

### 问答速查表

| 考点 | 一句话答案 |
|------|-----------|
| JVM 内存五块 | 程序计数器、虚拟机栈、本地方法栈、堆、方法区 |
| 线程私有 | 程序计数器、虚拟机栈、本地方法栈 |
| 线程共享 | 堆、方法区 |
| 哪个不会 OOM | 程序计数器 |
| 永久代 vs 元空间 | JDK 8 用本地内存的元空间替代堆内的永久代 |
| 对象分配顺序 | Eden → Survivor0 ↔ Survivor1 → Old |
| TLAB 是什么 | 线程本地分配缓冲，减少并发分配时的锁竞争 |

## 类加载机制

### 基础概念

JVM 把 Class 文件从磁盘加载到内存，经过验证、准备、解析、初始化，最终变成可以直接使用的 Class 对象，这个过程就是 **类加载**。

### 原理深入

#### 类加载的五个阶段

**加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载**

每个阶段做什么：

| 阶段 | 做什么 | 关键点 |
|------|--------|--------|
| 加载 | 通过类全限定名找到字节码，生成 Class 对象 | 可以自定义类加载器 |
| 验证 | 验证文件格式、元数据、字节码、符号引用 | 保证 JVM 安全 |
| 准备 | 为静态变量分配内存，设零值 | 此时 `static int a = 1` 还是 0 |
| 解析 | 符号引用 → 直接引用 | 可能在初始化后才执行 |
| 初始化 | 执行 `<clinit>()`，初始化静态变量 | 类加载的最后一步 |

> **关键**：准备阶段 vs 初始化阶段。`static int a = 1` 在准备阶段值为 0，到初始化阶段才被赋为 1。但 `static final int a = 1` 例外，编译期就确定了值，准备阶段直接赋值。

#### 双亲委派模型

```text
        Bootstrap ClassLoader（启动类加载器）
              │    加载：<JAVA_HOME>/lib（rt.jar 等）
              │
        Extension ClassLoader（扩展类加载器）JDK 9+ 改为 Platform
              │    加载：<JAVA_HOME>/lib/ext
              │
        Application ClassLoader（应用类加载器）
              │    加载：classpath 下的类
              │
        自定义 ClassLoader
```

**工作流程**：

1. 收到类加载请求，先检查是否已加载
2. 没加载则委派给父加载器去加载
3. 所有父加载器都加载不了，才由自己加载

**为什么用双亲委派**：

- 避免类的重复加载：相同全限定名只加载一次
- 安全：防止核心 API 被篡改，比如不能自己写一个 `java.lang.String` 去替换 JDK 的

**源码核心**（`ClassLoader.loadClass()`）：

```java
protected Class<?> loadClass(String name, boolean resolve) {
    synchronized (getClassLoadingLock(name)) {
        // 1. 检查是否已加载
        Class<?> c = findLoadedClass(name);
        if (c == null) {
            try {
                // 2. 委派给父加载器
                if (parent != null) {
                    c = parent.loadClass(name, false);
                } else {
                    c = findBootstrapClassOrNull(name);
                }
            } catch (ClassNotFoundException e) {
                // 父加载器找不到，自己加载
            }
            if (c == null) {
                // 3. 自己找
                c = findClass(name);
            }
        }
        return c;
    }
}
```

#### 破坏双亲委派

**场景一：SPI 机制（JDBC）**

DriverManager 由 BootStrap 加载，但具体驱动是 classpath 上的 jar。BootStrap 没法反向委托给子加载器，所以引入了 **线程上下文类加载器**，让父加载器"借用"子加载器去加载具体实现类。

**场景二：Tomcat 类加载**

每个 Web 应用需要隔离，防止不同应用的类冲突：

- 自己优先加载（WebappClassLoader 先自己找）
- Common 类共享（放 catalina/lib）

### 问答实战（精讲及回答）

#### ⭐⭐⭐ 说一下类加载过程

**提问意图**：JDK 经典题，看理解深度。

**推荐回答**：

> 五个阶段。加载阶段，通过类的全限定名获取字节流，可以是 class 文件、jar 包、网络甚至动态代理生成的，加载完成后创建一个代表该类的 Class 对象。
>
> 验证阶段确保字节码安全合法。准备阶段给静态变量分配内存并赋零值，注意 `static int a = 100` 这个阶段还是 0，只有 `static final` 修饰的常量在编译期就确定了值，准备阶段直接赋值。
>
> 解析阶段把常量池里的符号引用变成内存中的直接引用，比如把方法名引用解析成内存地址。
>
> 初始化阶段执行 `<clinit>()` 方法，由编译器按代码顺序收集所有静态变量的赋值和静态代码块合并而成，注意 `<clinit>()` 在多线程下是加锁执行的。

**追问准备**：

- "`<clinit>()` 和 `<init>()` 的区别？" → `<clinit>()` 是类初始化方法，执行静态变量赋值和静态代码块，由 JVM 保证线程安全。`<init>()` 是实例初始化方法，执行实例变量赋值、实例代码块、构造方法。`<init>()` 执行前会先调用父类的 `<init>()`。

---

#### ⭐⭐ 双亲委派模型是什么？为什么要这样设计？

**提问意图**：考察对类加载器模型的理解。

**推荐回答**：

> 双亲委派模型的核心就一句话：类加载时先问爸爸有没有加载过。类加载器收到请求后，自己不先尝试加载，而是逐级向上委派给父加载器，直到顶层的启动类加载器。顶层的都加载不了再回退到自己尝试加载。
>
> 两个好处。一是避免重复加载：父加载器加载过的类子加载器不再重复加载，保证每个类的唯一性。二是核心安全：你没法自己写一个 `java.lang.String` 放进 classpath 去替换 JDK 的 String，因为加载请求会被一直委派到 Bootstrap ClassLoader，而它只会加载 rt.jar 里的那个。

**追问准备**：

- "什么场景需要打破双亲委派？" → JDBC 的 SPI 机制，BootStrap 加载的 DriverManager 需要通过线程上下文类加载器去加载 classpath 上的具体驱动实现。Tomcat 的 Web 应用隔离，每个应用需要优先加载自己的类。

### 问答速查表

| 考点 | 一句话答案 |
|------|-----------|
| 五个阶段 | 加载 → 验证 → 准备 → 解析 → 初始化 |
| 三个阶段由类加载器完成 | 加载、验证、准备 |
| 第一个由 JVM 完成的阶段 | 解析 |
| 双亲委派核心 | 先委托父加载器加载，父不行再自己加载 |
| 为啥这样设计 | 避免重复加载、保护核心类不被篡改 |
| SPI 怎么打破 | 线程上下文类加载器，让 Bootstrap 借用 AppClassLoader |

## 垃圾回收（GC）

### 基础概念

GC（Garbage Collection）自动管理堆内存，回收不再使用的对象。Java 程序员不用手动 free 内存，但需要理解 GC 原理才能调优和排查问题。

### 原理深入

#### 怎么判断对象已死？

**引用计数法**（Java 不用）：每个对象维护一个引用计数器，引用为 0 时回收。缺点是无法解决 **循环引用**：`A <-> B`，互相引用但都没有外部引用，计数器永远不为 0。

**可达性分析**（Java 采用）：从一组 **GC Roots** 出发，向下搜索引用链，不在任何引用链上的对象判定为不可达，可以回收。

```text
GC Roots
    │
    ├── 可达对象（存活）
    │   ├── obj1
    │   │   └── obj2
    │   └── obj3
    │
    └── 不可达对象（可回收）
        ├── obj4 ──── obj5（循环引用，无 GC Root 可达）
        └── obj6
```

#### GC Roots 有哪些？

1. **虚拟机栈**中引用的对象（局部变量表中的引用）
2. **方法区中静态属性**引用的对象
3. **方法区中常量**引用的对象
4. **本地方法栈中 JNI** 引用的对象
5. **所有被同步锁（synchronized）持有的对象**
6. **JVM 内部的引用**（基本类型的 Class 对象、常驻异常对象等）

#### 三色标记法（CMS、G1 的底层算法）

标记顺序：**白色 → 灰色 → 黑色**。

| 颜色 | 含义 |
|------|------|
| 白色 | 未被访问过，初始都是白色 |
| 灰色 | 本对象访问了，但它的引用还没有全部处理完 |
| 黑色 | 本对象及其全部引用都已处理完 |

**工作过程**：

1. 从 GC Roots 出发，标为灰色
2. 取一个灰色节点，把它引用的对象标灰，自己变黑
3. 重复直到没有灰色节点
4. 剩下的白色就是要回收的

**漏标问题**：并发标记时，用户线程可能修改引用关系，导致本应存活的对象被错误回收。解决方式是 **写屏障 + SATB（Snapshot At The Beginning）**，G1 的做法是标记开始时拍快照，任何把字段从 null 变成非 null 的写入都被记录，这些新引用对象被视为存活。

#### 三大垃圾回收算法

| 算法 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| 标记-清除 | 标记可回收对象，直接清除 | 最简单 | 产生内存碎片 |
| 标记-复制 | 把存活对象复制到另一块区域，清空原区域 | 无碎片，效率高 | 浪费一半内存 |
| 标记-整理 | 标记后把存活对象移动到一端，清理边界外 | 无碎片，不浪费空间 | 移动对象有开销，需要 STW |

**实际应用**：

- 新生代用 **标记-复制**（Survivor 区 S0 ↔ S1）
- 老年代用 **标记-清除** 或 **标记-整理**

#### 分代收集理论

**弱分代假说**：绝大多数对象朝生夕死 → 新生代频繁 GC（Minor GC），回收快

**强分代假说**：活得越久的对象越难死 → 老年代减少 GC 频率（Major GC）

**跨代引用假说**：跨代引用只占极少数 → 用 **记忆集（Remembered Set）** 记录老年代引用了哪些新生代对象，Minor GC 时除了 GC Roots 还要扫描记忆集

### 问答实战（精讲及回答）

#### ⭐⭐⭐ 如何判断对象是否存活？GC Roots 有哪些？

**提问意图**：GC 高频考题，几乎必问。

**推荐回答**：

> Java 用的是可达性分析算法，不是引用计数。引用计数的致命弱点是循环引用——两个对象互相引用但外部没人用到它们，引用计数永远不为零，回收不掉。
>
> 可达性分析是从一组 GC Roots 出发，沿着引用链往下搜索。能到达的就是活的，到不了的就是死的。
>
> GC Roots 主要包括：虚拟机栈里的局部变量表引用的对象（当前在用的），方法区里静态属性和常量引用的对象（全局在用的），本地方法栈里 JNI 引用的对象，以及被 synchronized 持有的对象。

**追问准备**：

- "引用计数真的完全不用吗？" → 主流 JVM 都不用引用计数算法做 GC。但在一些嵌入式 JVM 或脚本语言中有使用。

---

#### ⭐⭐⭐ 三种 GC 算法的优缺点和使用场景

**提问意图**：考察对不同算法的理解，能不能说清楚"为什么新生代用复制、老年代用标记-整理"。

**推荐回答**：

> 标记-清除最简单：找到要回收的，直接清除。问题是会产生不连续的内存碎片，下次分配大对象时找不到连续空间可能触发 GC。
>
> 标记-复制解决了碎片问题：存活对象搬到另一块，原区域整体清空。缺点是预留区域一直空着用不上。但这个缺点在新生代反而不明显——因为绝大部分对象朝生夕死，Eden 区 98% 的对象都活不过第一次 GC，真正需要复制的只有极少量的存活对象，所以效率很高。
>
> 标记-整理没有碎片也不浪费空间：把存活对象全部往一端移动，然后一口气清理边界外。但移动对象需要 STW 暂停并更新所有引用，开销大。老年代对象存活率高，用复制算法代价太大（要复制一大堆存活对象），但用标记-清除又怕碎片。所以老年代平时用标记-清除，碎片积累到一定阈值时用标记-整理压缩一次。

---

#### ⭐⭐ 什么是 Stop The World？为什么必须 STW？

**提问意图**：考察对 GC 代价的认识。

**推荐回答**：

> Stop The World 就是 GC 发生时，所有用户线程必须暂停。原因是：如果用户线程一边跑一边改引用关系，GC 线程就没法准确地确定哪些对象是活的——类似于你在整理书架，有人不断把书拿走又放回来，你就永远整不完。
>
> 不同收集器的 STW 时间不同。Serial 简单粗暴，全程 STW。CMS 和 G1 只在初始标记和重新标记阶段 STW，大部分标记和清除过程与用户线程并发执行，大幅降低了暂停时间。

### 问答速查表

| 考点 | 一句话答案 |
|------|-----------|
| 判断死亡算法 | 可达性分析（不是引用计数） |
| GC Roots 有哪些 | 栈帧引用、静态属性、常量、JNI、同步锁 |
| 三大算法 | 标记-清除、标记-复制、标记-整理 |
| 新生代用哪个 | 标记-复制 |
| 老年代用哪个 | 标记-清除（碎片多时标记-整理） |
| 三色标记 | 白灰黑，白色是要回收的 |
| STW 是什么 | GC 暂停所有用户线程 |

## 垃圾回收器

### 基础概念

垃圾回收器是 GC 算法的具体实现。不同回收器适用于不同场景，JDK 的默认回收器经历了 Serial → Parallel → CMS → G1 的演变。

### 原理深入

#### 回收器一览

| 回收器 | 目标区域 | 线程数 | 算法 | STW | 使用场景 |
|--------|---------|--------|------|-----|---------|
| Serial | 新生代 | 单线程 | 标记-复制 | 全程 STW | 客户端、单核 |
| ParNew | 新生代 | 多线程 | 标记-复制 | 全程 STW | 配合 CMS |
| Parallel Scavenge | 新生代 | 多线程 | 标记-复制 | 全程 STW | 吞吐量优先 |
| Serial Old | 老年代 | 单线程 | 标记-整理 | 全程 STW | 客户端、备胎 |
| Parallel Old | 老年代 | 多线程 | 标记-整理 | 全程 STW | 吞吐量优先 |
| CMS | 老年代 | 多线程 | 标记-清除 | 短暂 STW | 低延迟 |
| G1 | 整堆 | 多线程 | 标记-整理+复制 | 短暂 STW | 平衡吞吐与延迟 |
| ZGC | 整堆 | 多线程 | 标记-复制 | `<10ms` | 超低延迟 |
| Shenandoah | 整堆 | 多线程 | 标记-复制 | `<10ms` | 超低延迟 |

#### Parallel Scavenge + Parallel Old（吞吐量优先）

- **唯一目标**：在 CPU 时间内跑尽可能多的用户代码
- 通过 `-XX:MaxGCPauseMillis` 和 `-XX:GCTimeRatio` 控制
- 适合后台计算、批处理

#### CMS（Concurrent Mark Sweep，低延迟）

| 阶段 | 是否 STW | 做什么 |
|------|---------|--------|
| 1. 初始标记（Initial Mark） | ✅ 是，时间很短 | 只标记 GC Roots 能直接关联到的对象 |
| 2. 并发标记（Concurrent Mark） | ❌ 否，与用户线程并发 | 从 GC Roots 开始，递归遍历整个对象图 |
| 3. 重新标记（Remark） | ✅ 是，时间稍长 | 修正并发标记期间用户线程修改的引用 |
| 4. 并发清除（Concurrent Sweep） | ❌ 否，与用户线程并发 | 清除不可达对象，回收内存 |

**CMS 的三大问题**：

1. **并发标记时 CPU 竞争**——占用一部分 CPU，吞吐量下降
2. **浮动垃圾**——并发清除阶段新产生的垃圾只能等下一次 GC
3. **内存碎片**——标记-清除算法的固有缺点，碎片太多时退化为 Serial Old 做标记-整理

#### G1（Garbage First）

**核心理念**：不再分固定的新生代和老年代，而是把堆切分成多个大小相等的 **Region**。每个 Region 可以在逻辑上作为 Eden、Survivor 或老年代。

```text
G1 堆结构
┌───┬───┬───┬───┬───┬───┬───┬───┐
│ E │ S │ O │ E │ H │ E │ O │ E │
├───┼───┼───┼───┼───┼───┼───┼───┤
│ E │ E │ O │ E │ S │ O │ E │ E │
└───┴───┴───┴───┴───┴───┴───┴───┘
E=Eden  S=Survivor  O=Old  H=Humongous（大对象专用）

每个 Region 默认 2MB（可通过 -XX:G1HeapRegionSize 调整）
```

**G1 核心概念**：

**RSet（Remembered Set）**：每个 Region 维护一个 RSet，记录「谁引用了我的对象」。避免全堆扫描跨 Region 引用。

**SATB（Snapshot At The Beginning）**：并发标记的开始阶段拍一张逻辑快照，标记阶段新创建的对象默认存活（通过写屏障保证）。

**Mixed GC**：G1 不仅做 Young GC，还会选择性地回收部分老年代 Region。选择标准是回收收益最高的——即"垃圾最多的 Region 先回收"，这也是 Garbage First 名字的来源。

#### G1 vs CMS

| 对比项 | CMS | G1 |
|--------|-----|-----|
| 内存模型 | 固定分代 | Region 化 |
| 碎片 | 有（标记-清除） | 无（整体看是标记-整理） |
| 停顿时间 | 可预测性差 | 可指定期望停顿时间 |
| 大对象 | 直接进老年代 | 有 Humongous Region |
| 调优参数 | 较多 | 相对少 |
| JDK 状态 | JDK 14 移除 | JDK 9+ 默认 |

### 问答实战（精讲及回答）

#### ⭐⭐⭐ CMS 的回收流程是怎样的？有什么缺点？

**提问意图**：考察对 CMS 内部机制的理解，这是中高级面试常问题。

**推荐回答**：

> CMS 分四个阶段。初始标记很快，只标记 GC Roots 直连的对象，需要 STW。第二阶段并发标记，遍历整个对象图，和用户线程并发跑，时间最长但不暂停。第三阶段重新标记，修正并发标记期间被用户线程改掉的引用关系，也需要 STW。最后并发清除，回收垃圾对象。
>
> 三个明显缺点。一是并发标记和清除阶段占用 CPU 资源，吞吐量会下降。二是浮动垃圾——并发清除过程中用户线程新产生的垃圾这次回收不了，只能等下次。最严重的是内存碎片，因为用的是标记-清除算法，碎片多了会触发 Concurrent Mode Failure，退化为 Serial Old 做一次全堆的标记-整理，这个停顿时间会非常长。

**追问准备**：

- "什么是 Concurrent Mode Failure？" → 并发清除阶段老年代剩余空间不够分配了，CMS 会失败，JVM 退而使用 Serial Old 做一次 Full GC，单线程标记-整理，停顿时间特别长。

---

#### ⭐⭐⭐ G1 和 CMS 有什么区别？为什么 G1 替代了 CMS？

**提问意图**：考察对现代 GC 的理解，以及 JDK 演进方向的认知。

**推荐回答**：

> 最核心的区别是内存模型。CMS 是传统的固定分代，G1 把堆切分成等大小的 Region，每个 Region 可以动态扮演 Eden、Survivor 或老年代的角色。
>
> 回收策略上，CMS 只能整个老年代一起回收。G1 可以做 Mixed GC——只回收垃圾最多的几个 Region，用可控的代价回收尽可能多的垃圾。这种"性价比优先"的策略让 G1 的停顿时间更可预测。
>
> 碎片问题上，CMS 用标记-清除会产生碎片，碎片严重时要退化为 Serial Old 做全堆标记-整理。G1 回收时把存活对象复制到新的 Region，本质是标记-整理，不会产生碎片。
>
> 还有一个是调优体验。CMS 参数多，要调得好不容易。G1 你只需要设一个期望的停顿时间 `-XX:MaxGCPauseMillis`，JVM 自己尽量满足，调优参数少很多。

---

#### ⭐⭐ G1 的 Region、RSet、SATB 分别是什么？

**提问意图**：深入 G1 核心概念，看是不是真正理解。

**推荐回答**：

> Region 是 G1 内存管理的基本单位，不再有固定的新生代/老年代边界。每个 Region 大小固定（默认约 2MB），可以在逻辑上做 Eden、Survivor 或老年代。大对象有专用的 Humongous Region。
>
> RSet 是记住集，每个 Region 存一份，记录「外部谁引用了我」。这样 Minor GC 或 Mixed GC 时不用扫描全堆，只扫描 RSet 里记录的引用来源就行，极大降低了跨 Region 引用的扫描开销。
>
> SATB 是并发标记时的快照机制。初始标记时拍一张逻辑快照，标记过程中新创建的对象默认认为是活的，避免把这些对象误回收。这个机制依赖写屏障（write barrier）来实现。

### 问答速查表

| 考点 | 一句话答案 |
|------|-----------|
| 新生代回收器 | Serial、ParNew、Parallel Scavenge |
| 老年代回收器 | Serial Old、Parallel Old、CMS |
| 整堆回收器 | G1、ZGC、Shenandoah |
| CMS 四个阶段 | 初始标记(STW) → 并发标记 → 重新标记(STW) → 并发清除 |
| CMS 三大问题 | CPU 竞争、浮动垃圾、内存碎片 |
| JDK 9+ 默认 | G1 |
| G1 核心概念 | Region、RSet、SATB、Mixed GC |
| G1 为什么叫 Garbage First | 优先回收垃圾最多的 Region |

## JVM 调优与参数

### 基础概念

JVM 提供了大量的参数来控制内存大小、GC 行为、日志输出等。生产环境调优的核心目标是：**在可接受的停顿时间内，最大化吞吐量**。

### 常用 JVM 参数速查

#### 堆与分代大小

| 参数 | 作用 | 示例 |
|------|------|------|
| `-Xms` | 初始堆大小 | `-Xms2g` |
| `-Xmx` | 最大堆大小 | `-Xmx4g` |
| `-Xmn` | 新生代大小 | `-Xmn1g` |
| `-XX:NewRatio` | 老年代/新生代比例 | `-XX:NewRatio=2`（老年代:新生代=2:1） |
| `-XX:SurvivorRatio` | Eden/Survivor 比例 | `-XX:SurvivorRatio=8`（Eden:S0:S1=8:1:1） |

#### 元空间

| 参数 | 作用 |
|------|------|
| `-XX:MetaspaceSize` | 触发 Full GC 的阈值 |
| `-XX:MaxMetaspaceSize` | 元空间最大大小（不设则无限制） |

#### GC 选择

| 参数 | 回收器 |
|------|--------|
| `-XX:+UseSerialGC` | Serial + Serial Old |
| `-XX:+UseParallelGC` | Parallel Scavenge + Serial Old |
| `-XX:+UseParallelOldGC` | Parallel Scavenge + Parallel Old |
| `-XX:+UseConcMarkSweepGC` | ParNew + CMS |
| `-XX:+UseG1GC` | G1（JDK 9+ 默认） |
| `-XX:+UseZGC` | ZGC（JDK 11+） |

#### G1 核心参数

| 参数 | 作用 | 默认值 |
|------|------|--------|
| `-XX:MaxGCPauseMillis` | 期望最大停顿时间（ms） | 200 |
| `-XX:G1HeapRegionSize` | Region 大小（1/2/4/8/16/32M） | 按堆大小自动算 |
| `-XX:InitiatingHeapOccupancyPercent` | 老年代占比阈值，触发 Mixed GC | 45 |
| `-XX:G1NewSizePercent` | 新生代最小占比 | 5 |
| `-XX:G1MaxNewSizePercent` | 新生代最大占比 | 60 |

#### GC 日志（JDK 8）

| 参数 | 作用 |
|------|------|
| `-XX:+PrintGCDetails` | 打印 GC 详情 |

| `-XX:+PrintHeapAtGC` | GC 前后打印堆信息 |
| `-Xloggc:/path/to/gc.log` | GC 日志输出路径 |

#### GC 日志（JDK 9+ 统一日志）

```bash
-Xlog:gc*:file=/path/to/gc.log:time,level,tags
```

#### 常用配置模板

**4G 堆，G1，低延迟**：

```bash
-Xms4g -Xmx4g -XX:+UseG1GC -XX:MaxGCPauseMillis=100
-XX:+PrintGCDetails -Xloggc:/var/log/gc.log
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/
```

**2G 堆，高吞吐，后台计算**：

```bash
-Xms2g -Xmx2g -XX:+UseParallelGC -XX:ParallelGCThreads=4
```

### 调优思路

**问题现象 → 排查步骤 → 确定瓶颈 → 调整参数 → 验证效果**

```text
现象1：频繁 Full GC
    ├── 检查老年代增长曲线（GC 日志）
    ├── 可能原因：老年代太小 / 内存泄漏 / 大对象直接进老年代
    └── 解决：调大 -Xmx / 调高 NewRatio / 检查代码

现象2：每次 Young GC 时间长
    ├── 可能原因：Survivor 区太小，对象被迫进老年代
    └── 解决：调小 SurvivorRatio / 调大 -Xmn

现象3：OOM
    ├── 导出 heap dump（-XX:+HeapDumpOnOutOfMemoryError）
    ├── 用 MAT / JProfiler 分析
    └── 确认是内存泄漏还是峰值流量
```

### 问答实战（精讲及回答）

#### ⭐⭐⭐ 线上 OOM 了怎么排查？

**提问意图**：考察真实问题的排查能力，这是面试高频场景题。

**推荐回答**：

> 第一步，确认 OOM 的类型。看日志里的 `java.lang.OutOfMemoryError` 后面跟什么——是 Java heap space、GC overhead limit exceeded、Metaspace 还是 Direct buffer memory，不同原因排查方向完全不同。
>
> 堆空间 OOM 最常见。启动时就加上 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path/`，出问题时自动 dump 堆快照。拿到 dump 后用 MAT 或 JProfiler 打开，看 Dominator Tree——按占用内存从大到小一排，最大的那个基本就是问题所在。常见的是某个集合类里塞了大量没用的对象，或者缓存没有淘汰机制导致泄漏。
>
> 如果没有 dump 文件又不方便重启加参数，可以先用 `jmap -histo <pid>` 看看哪些类的实例数量异常多，也能缩小排查范围。`jstat -gc <pid> 1000` 实时观察 GC 情况，看老年代是不是一直涨不回收——那就是泄漏。

**追问准备**：

- "GC overhead limit exceeded 是什么意思？" → GC 占用了 98% 以上的 CPU 时间但每次只回收不到 2% 的堆内存，JVM 判断这个状态再继续也只是空耗 CPU，直接抛 OOM。本质也是堆太小，增大堆或排查是否有对象一直占着不放。

---

#### ⭐⭐ 频繁 Full GC 怎么排查和解决？

**提问意图**：考察 GC 调优的实际经验。

**推荐回答**：

> 从现象倒推。在 GC 日志里看 Full GC 的触发原因。如果是 `Ergonomics`——说明老年代剩余空间不够了，得排查是什么东西频繁进老年代。可能是指定了大对象直接进年老代的阈值太小，或者 Survivor 区太小对象被迫晋升。
>
> 如果是 `System.gc()` 触发——代码里有人手动调了 GC，建议用 `-XX:+DisableExplicitGC` 禁用。
>
> 如果是 `Metadata GC Threshold`——元空间不够了，调大 `-XX:MaxMetaspaceSize` 或检查是不是动态代理、反射加载了太多类。
>
> 用 `jstat -gc <pid> 1000` 看实时数据：YGC 和 YGCT 看新生代 GC 频率和耗时，FGC 和 FGCT 看 Full GC 频率和耗时。如果 FGC 频率远高于 YGC，老年代肯定有问题。

### 问答速查表

| 考点 | 一句话答案 |
|------|-----------|
| 设置堆大小 | `-Xms` 初始，`-Xmx` 最大 |
| 设置新生代大小 | `-Xmn` |
| 设置元空间 | `-XX:MetaspaceSize` / `-XX:MaxMetaspaceSize` |
| 指定 G1 | `-XX:+UseG1GC` |
| G1 期望停顿 | `-XX:MaxGCPauseMillis=<ms>` |
| OOM 自动 dump | `-XX:+HeapDumpOnOutOfMemoryError` |
| OOM 排查思路 | 看 OOM 类型 → jmap/jstat → MAT 分析 dump |

## 强 / 软 / 弱 / 虚引用

### 基础概念

Java 提供了四种引用类型，控制 GC 时对象的回收行为。从强到弱依次是 **强引用 → 软引用 → 弱引用 → 虚引用**：强引用绝不回收，软引用内存不足才回收，弱引用下次 GC 就回收，虚引用最弱、随时回收。

### 原理深入

#### 四种引用对比

| 引用类型 | 回收时机 | 用途 |
|----------|---------|------|
| 强引用（Strong） | 永不回收（变量还在作用域内） | 99% 的引用 |
| 软引用（Soft） | 内存不足时回收 | 缓存（图片缓存） |
| 弱引用（Weak） | 下次 GC 必定回收 | WeakHashMap、ThreadLocal |
| 虚引用（Phantom） | 任何时候，仅通知 | 堆外内存回收、对象终结监控 |

#### 软引用（SoftReference）

```java
SoftReference<byte[]> softRef = new SoftReference<>(new byte[1024 * 1024 * 10]);

byte[] data = softRef.get();  // 内存够时返回对象，不够时返回 null
```

**应用场景**：图片缓存、需要缓存但又不能撑爆内存的场景。内存充足时通过 get() 拿到缓存，OOM 前 GC 会自动回收。

#### 弱引用（WeakReference）

```java
WeakReference<User> weakRef = new WeakReference<>(new User());

User user = weakRef.get();    // GC 前有值
System.gc();                   // 触发 GC
user = weakRef.get();         // null，被回收了
```

**WeakHashMap**：Key 是弱引用，当 Key 没有外部强引用时，下次 GC 会自动移除 Entry，适合做缓存又不怕内存泄漏。

#### 虚引用（PhantomReference）

**最特殊的引用**：`get()` 永远返回 null，存在的意义是对象被回收时收到通知。

必须和 **ReferenceQueue** 配合使用。当 GC 发现虚引用指向的对象被回收时，会把虚引用放入关联的队列，应用程序可以从队列中取出虚引用，执行清理操作。

**典型场景**：NIO 的 `DirectByteBuffer` 分配直接内存后，Cleaner（继承 PhantomReference）被放入队列，后台线程从队列取出并调用 `unsafe.freeMemory()` 释放堆外内存。

#### ThreadLocal 为什么用弱引用？

```java
// ThreadLocal.ThreadLocalMap.Entry 的源码（简化）
static class Entry extends WeakReference<ThreadLocal<?>> {
    Object value;

    Entry(ThreadLocal<?> k, Object v) {
        super(k);          // Key 是弱引用
        this.value = v;    // Value 是强引用
    }
}
```

```text
Thread
  └── ThreadLocalMap
        └── Entry
              ├── key（弱引用 → ThreadLocal 实例）
              └── value（强引用 → 存入的对象）
```

**设计意图**：如果 Key 是强引用，只要线程不销毁，ThreadLocalMap 就一直持有 ThreadLocal，ThreadLocal 就永远无法被 GC。用弱引用后，当外部没有强引用指向 ThreadLocal 时，Key 可以正常回收。

**但这引入了内存泄漏的新问题**：Key 被回收变成了 null，但 Value 还强引用着不会回收。这就是为什么 ThreadLocal 必须在 `finally` 块里调用 `remove()`——它清理的是 Entry 本身，断开对 Value 的强引用。

### 问答实战（精讲及回答）

#### ⭐⭐⭐ 强引用、软引用、弱引用、虚引用的区别和使用场景

**提问意图**：经典高频题。

**推荐回答**：

> 从强到弱说。强引用是最常见的，只要引用还在作用域内对象就不会被回收。软引用会在内存不足时被 GC 回收，适合实现敏感缓存——内存够的时候用缓存加速，快 OOM 时让 GC 自动清理。弱引用比软引用更弱，下次 GC 时不管内存够不够都会被回收，主要用于 WeakHashMap 和 ThreadLocal 的 Key。虚引用最特殊，它本身拿不到对象——`get()` 永远返回 null，它唯一的价值是跟 ReferenceQueue 配合，当对象被回收时收到通知，做堆外内存释放这种清理工作。

---

#### ⭐⭐ ThreadLocal 为什么用弱引用？内存泄漏是怎么回事？

**提问意图**：考察 ThreadLocal 的设计和内存泄漏问题，初中级高频题。

**推荐回答**：

> ThreadLocal 被 ThreadLocalMap 的 Entry 用弱引用做 Key。设计目的是让 ThreadLocal 实例本身能被正常回收——如果 Key 用强引用，只要线程不销毁，ThreadLocal 就一直被 ThreadLocalMap 引用着没法被 GC。
>
> 但用弱引用的代价是内存泄漏风险。Entry 的结构是 Key 弱引用、Value 强引用。Key 被回收变成 null 后，Value 还强引用着没法回收。这些 null Key 的 Entry 会一直跟着线程生命周期，线程池里线程复用的时候就越积越多。
>
> ThreadLocal 本身有防御机制：在 get、set、remove 时会顺便清理掉 null Key 的 Entry。但如果你不主动调 remove，Value 仍然可能长时间泄漏。所以最可靠的做法是：用完就 `finally { threadLocal.remove(); }`。

**追问准备**：

- "怎么判断 ThreadLocal 内存泄漏？" → 用 MAT 分析 heap dump，按线程分组看 ThreadLocalMap 的 Entry 数量和大小。大量 null Key 的 Entry 就是泄漏信号。

| 考点 | 一句话答案 |
|------|-----------|
| 强引用 | 永不回收，默认引用 |
| 软引用 | 内存不足时回收，适合图片缓存 |
| 弱引用 | 下次 GC 必定回收，ThreadLocal / WeakHashMap |
